# ربات وب‌هوک کلینیک — بک‌اندِ Next.js برای Vercel 🤖

یک بک‌اندِ **فقط-سرور** (بدون هیچ صفحهٔ React) که:

1. حرف **فارسی** کاربر را می‌خواند و می‌فهمد چه کاری می‌خواهد؛
2. با **مدل‌های مجانیِ OpenRouter** فکر می‌کند؛
3. آن کار را از طریق **وب‌هوک‌های پروژهٔ فعلی** (‎`/api/v1/webhooks/*`) انجام می‌دهد؛
4. نتیجه را با **زبان ساده، در سطح فهمِ یک بچهٔ ۱۰ ساله** توضیح می‌دهد.

> **یک جمله‌ای:** «نوبت‌های امروز رو نشون بده» → ربات می‌فهمد، درخواست درست را می‌فرستد، و جواب می‌دهد: «بفرما، ۳ نوبت پیدا کردم: ۱. مریم رضایی — پرداخت‌شده …»
>
> **و در تلگرام:** بعد از هر استارت خودش لاگین می‌کند، و هوش مصنوعی برای هر جواب **دکمه می‌سازد** و **قدم بعدی را پیشنهاد می‌دهد**.

---

## این پروژه دقیقاً کجاست؟ (نقش «واسط»)

```
   ┌───────────────────────────────────────────┐
   │  nafasbeautyclinic.ir   (upstream)        │
   │  صاحب داده‌ها + صاحب /api/v1/webhooks/*   │
   └───────────────────▲───────────────────────┘
                       │  Basic Auth
                       │  رمز فقط در env همین پروژه است
   ┌───────────────────┴───────────────────────┐
   │  همین پروژه روی Vercel   (middleware)     │
   │  • /api/chat   → فهمیدن فارسی + اجرا       │
   │  • /api/proxy  → پاس‌دادن خام و کنترل‌شده   │
   │  • /api/telegram → ربات تلگرام + دکمه‌ها   │
   │  • rate limit + audit log + allowlist     │
   └───────────────────▲───────────────────────┘
                       │  webhook + دکمه‌ها (بدون AI برای منوها)
                       │  x-bot-key  (+ CORS برای مرورگر)
   ┌───────────────────┴───────────────────────┐
   │  پروژهٔ شما روی Vercel   (downstream)      │
   │  اپ / ربات / پنل مدیریت                   │
   └───────────────────────────────────────────┘
```

چرا واسط؟ چون:

1. **رمز سایت جای دیگری نمی‌رود.** پروژهٔ ورسلی و مرورگر کاربر هرگز `WEBHOOK_PASSWORD` را نمی‌بینند.
2. **سطح حملهٔ سایت کوچک می‌شود.** فقط ۴۹ اکشنِ منیفست از این در رد می‌شوند؛ `/api/proxy` یک پروکسی باز نیست.
3. **یک‌جا لاگ و محدودیت نرخ.** همهٔ درخواست‌ها از یک نقطه رد می‌شوند و `x-request-id` مشترک دارند.
4. **سایت لازم نیست CORS بدهد** یا کلید جدید بسازد.

دو حالتِ استفاده:

| حالت | مسیر | کِی |
| --- | --- | --- |
| **هوشمند** | `POST /api/chat` | کاربر فارسی می‌نویسد و باید خودش فهمیده شود |
| **واسط خام** | `GET/POST/PATCH/DELETE /api/proxy/api/v1/webhooks/…` | برنامهٔ تو از قبل می‌داند چه درخواستی می‌خواهد (سریع‌تر، بدون هزینهٔ مدل) |

## چرا این‌طوری ساخته شده

مدل‌های مجانی خوب‌اند ولی سه ضعف دارند: **کم‌حافظه‌اند، گاهی جواب بی‌ربط می‌دهند، و سهمیه‌شان (rate limit) زود تمام می‌شود.**
پس معماری این‌طور چیده شده که ضعف مدل، خرابیِ ربات نشود:

| مشکل مدل مجانی | جوابِ این پروژه |
| --- | --- |
| سهمیه تمام می‌شود (۴۲۹) | **زنجیرهٔ مدل‌ها**: ۵ مدل مجانی پشت سر هم؛ اولی که جواب بدهد برنده است |
| JSON خراب می‌دهد | سه لایهٔ بازیابی: `parseJsonLoose` → درخواست ترمیم → اعتبارسنجی Zod |
| کارِ اشتباه انتخاب می‌کند | **منیفست** فقط ۴۹ اکشن مجاز دارد؛ مدل نمی‌تواند آدرس یا دسترسی بسازد |
| کلاً قطع می‌شود | **موتور کلمات کلیدی** (بدون AI) همان کار را انجام می‌دهد و جواب‌ها هم نسخهٔ آمادهٔ فارسی دارند |
| ولخرج است در جمله‌سازی | «فهمیدن» و «توضیح دادن» دو فراخوانی جدا با دو پرامپت جدا هستند |

نتیجه: حتی اگر کلید OpenRouter خالی باشد، ربات بالا می‌آید، لیست نوبت‌ها را نشان می‌دهد، حذف را با تأیید انجام می‌دهد — فقط «فهمیدن» ساده‌تر می‌شود.


## شروع سریع

```bash
npm install

# ۱) کلید مجانی OpenRouter بگیر: https://openrouter.ai/keys
cp .env.example .env.local
#   OPENROUTER_API_KEY=sk-or-v1-...
#   WEBHOOK_BASE_URL=https://پروژهٔ-فعلی-شما
#   WEBHOOK_USERNAME / WEBHOOK_PASSWORD  (کاربر سرویسی که دسترسی‌ها را دارد)

# ۲) اول ببین به سایت واقعی می‌رسی یا نه، و کلیدت کار می‌کند یا نه:
npm run doctor      # DNS/TLS + مسیر وب‌هوک + اعتبار کلید + جدول مجوزها + مدل‌های مجانی

# ۳) اجرا (دو ترمینال):
npm run mock-api    # شبیه‌ساز سایت، برای کارِ محلی بدون دست‌زدن به دادهٔ واقعی
npm run dev         # واسط روی http://127.0.0.1:3000

# ۴) تلگرام (اختیاری، ۳۰ ثانیه):
#    توکن از @BotFather، بعد:
npm run telegram:setup

# ۵) تست:
npm run selftest    # ۴۵ تست، بدون نیاز به کلید و اینترنت
npm run smoke       # تست HTTP روی سرور در حال اجرا
npm run models      # کدام مدل مجانی الان زنده است؟
```

سپس مرورگر: `http://127.0.0.1:3000` (صفحهٔ مستندات + کنسول گفت‌وگو)
یا:

```bash
curl -s -X POST http://127.0.0.1:3000/api/chat \
  -H 'Content-Type: application/json' \
  -d '{"message":"نوبت‌های امروز رو نشون بده","sessionId":"demo"}'
```

## متغیرهای محیطی

| کلید | لازم؟ | توضیح |
| --- | --- | --- |
| `OPENROUTER_API_KEY` | ✅ | کلید OpenRouter. خالی باشد → ربات با موتور کلمات کلیدی کار می‌کند. |
| `OPENROUTER_MODELS` | – | زنجیرهٔ مدل‌های مجانی (با کاما). پیش‌فرض: ۵ مدل `:free`. کد خودش `:free` را تضمین می‌کند. |
| `WEBHOOK_BASE_URL` | ✅ | آدرس upstream. پیش‌فرض: `https://nafasbeautyclinic.ir` |
| `WEBHOOK_USERNAME` | ✅ | ایمیل کاربر سرویس (Basic Auth). |
| `WEBHOOK_PASSWORD` | ✅ | رمز آن کاربر. |
| `BOT_API_KEY` | ⚠️ پروداکشن | اگر پر شود، `/api/chat` و `/api/proxy` فقط با هدر `x-bot-key` (یا `Authorization: Bearer`) جواب می‌دهند. |
| `ALLOWED_ORIGINS` | – | دامنه‌های مجاز برای فراخوانی از مرورگر (CORS)، با کاما. خالی = فقط سرور-به-سرور. `*` = همه. |
| `CHAT_RATE_LIMIT` / `CHAT_RATE_WINDOW_MS` | – | پیش‌فرض ۲۰ پیام در ۶۰ ثانیه برای هر IP. |
| `ALLOW_AUTO_WRITE` | – | `true` = نوشتن‌های غیرمخرب بدون کارت تأیید. **حذف هرگز** خودکار نیست. |
| `MODEL_TIMEOUT_MS` / `MODEL_RETRIES` | – | ۴۵ ثانیه / ۲ تلاش برای هر مدل. |
| `DEFAULT_LOCALE` | – | `fa` (پیش‌فرض) یا `en`. |
| `TELEGRAM_BOT_TOKEN` | – | توکن از @BotFather. خالی = ربات تلگرام خاموش. |
| `TELEGRAM_WEBHOOK_SECRET` | ⚠️ با تلگرام | با `openssl rand -hex 32` بساز؛ جلوی آپدیت جعلی را می‌گیرد. |
| `PUBLIC_APP_URL` | – | آدرس https همین پروژه، برای ثبت وب‌هوک. |
| `TELEGRAM_ALLOWED_CHAT_IDS` | ⚠️ پروداکشن | چت‌های مجاز، با کاما. عدد را با `/id` بگیر. |
| `TELEGRAM_AUTO_SETUP` | – | `true` (پیش‌فرض) = بعد از استارت خودکار ثبت کن. |
| `TELEGRAM_API_BASE` | – | فقط برای دمو/پروکسی (پیش‌فرض `api.telegram.org`). |
| `TELEGRAM_REQUIRE_IDENTITY` | ⚠️ پیشنهاد | `true` = هر چت باید با شمارهٔ تلگرامش در «کاربران» سایت پیدا شود (ورود بدون رمز). |

## مدل‌های مجانی OpenRouter

زنجیرهٔ پیش‌فرض (بر اساس `GET /api/v1/models` امروز، همه `:free` و همه با پشتیبانی `tools` + `response_format`):

```
google/gemma-4-31b-it:free
nvidia/nemotron-3.5-super-vl:free
xingchen-agi/xing4.0-29b-a4b:free
google/gemma-4-26b-a4b-it:free
liquid/lfm-3-1.7b:free
```

- مدل‌های مجانی **می‌آیند و می‌روند**. هر وقت خطا دیدی: `npm run models` → اگر مدلی «✗ gone» بود، جایگزین پیشنهادی را در `OPENROUTER_MODELS` بگذار.
- ترتیب مهم است: مدل بزرگ‌تر اول (فهمِ فارسیِ بهتر)، مدل کوچک و سریع آخر (تأخیر کمتر، ولی همیشه یک جواب).
- همه‌چیز فقط با `:free` کار می‌کند؛ `config.ts` اگر پسوند نداشته باشد خودش اضافه می‌کند تا اشتباهی پول خرج نشود.

## API

### `POST /api/chat`

```jsonc
{
  "message": "نوبت‌های پرداخت‌نشده را نشان بده",
  "sessionId": "user-123",     // اختیاری: حافظهٔ گفت‌وگو + تأییدیه
  "locale": "fa",
  "dryRun": false,             // اختیاری: هیچ نوشتنی اجرا نشود
  "confirm": { "token": "...", "approve": true }   // پاسخ به کارت تأیید
}
```

```jsonc
{
  "ok": true,
  "data": {
    "status": "done",                  // answered | needs_info | needs_confirmation | done | error
    "reply": "بفرما، ۲ نوبت پیدا کردم: …",
    "understood": "می‌خواهی نوبت‌های پرداخت‌نشده را ببینی.",
    "intent": "read",
    "actionId": "bookings.list",
    "result": { "ok": true, "httpStatus": 200, "data": { "items": [...] } },
    "trace": { "planner": "ai", "writer": "ai", "plannerModel": "google/gemma-4-31b-it:free", "ms": 1840 }
  }
}
```

**چهار حالتِ پاسخ:**

| status | یعنی چه | کار تو |
| --- | --- | --- |
| `answered` | فقط حرف زد (سلام، «چه کارهایی بلدی؟») | – |
| `needs_info` | اطلاعات کم است | به `questions` جواب بده |
| `needs_confirmation` | می‌خواهد چیزی را تغییر دهد | با همان `confirmation.token` دوباره صدا بزن |
| `done` / `error` | انجام شد / نشد | `result` و `reply` را ببین |

### `ALL /api/proxy/api/v1/webhooks/…` — حالت واسط

اگر برنامهٔ تو از قبل می‌داند چه می‌خواهد، AI لازم نیست:

```bash
# لیست نوبت‌های پرداخت‌نشده، از طریق واسط
curl -s "https://<middleware>.vercel.app/api/proxy/api/v1/webhooks/bookings?status=pending&perPage=5" \
  -H "x-bot-key: $BOT_API_KEY"

# تغییر وضعیت یک نوبت
curl -s -X PATCH "https://<middleware>.vercel.app/api/proxy/api/v1/webhooks/bookings/<uuid>" \
  -H "x-bot-key: $BOT_API_KEY" -H 'Content-Type: application/json' \
  -d '{"status":"done"}'
```

- پاسخ، **همان پوشش سایت** است: `{ ok: true, data }` یا `{ ok: false, error: { code, message } }` + `x-request-id`.
- مسیر/متدی که در منیفست نیست → `404 NOT_ALLOWED` (پروکسیِ باز نیست).
- فهرست مجازها: `GET /api/features`.

## 📱 ربات تلگرام (لاگین خودکار + دکمه‌های هوش مصنوعی)

### چرا «لاگین»؟

ربات تلگرام صفحهٔ ورود ندارد. معادلِ لاگین سه خط است و ما همه‌اش را خودکار می‌کنیم:

```
getMe()        → «من کی‌ام؟»           → @YourBot ✅
setWebhook()   → «آدرسم این است»        → https://<app>/api/telegram/webhook
getWebhookInfo() → «ثبت شد؟»            → pending_update_count = 0
```

**کِی اتفاق می‌افتد؟** هر بار که سرور بالا می‌آید — `instrumentation.ts` → `register()` → `autoSetupOnBoot()`.
یعنی روی Vercel با اولین درخواست/کولد-استارت، و محلی با `npm run dev`.
`getMe` همیشه اجرا می‌شود، ولی `setWebhook` فقط وقتی لازم است (URL عوض شده باشد) — پس ری‌استارت‌ها ثبت را الکی تکرار نمی‌کنند.

دستی هم داری:

```bash
npm run telegram:setup             # ثبت/تعمیر وب‌هوک + نمایش لینک t.me
npm run telegram:setup -- --force  # ثبت دوباره
npm run telegram:setup -- --drop   # دور ریختن صف آپدیت‌ها
```

```bash
# همین کار از طریق HTTP (مثلاً از CI یا پنل):
GET  /api/telegram/setup                 # فقط وضعیت
POST /api/telegram/setup {"force":true}   # ثبت/تعمیر
POST /api/telegram/setup {"logout":true}  # حذف وب‌هوک
```
همه‌شان `x-bot-key` می‌خواهند.

### دکمه‌ها را هوش مصنوعی می‌سازد

بعد از هر جواب، یک فراخوانی کوچک از مدل مجانی می‌پرسد: «این کاربر اگر من بودم، الان چه چیزی را فشار می‌داد؟»
جواب JSON است و **قبل از ساختن دکمه اعتبارسنجی می‌شود**:

| قاعده | چرا |
| --- | --- |
| `actionId` باید در منیفست باشد | مدل نمی‌تواند دکمهٔ ساختگی بسازد |
| فقط اکشن‌های `read` | هیچ دکمه‌ای «حذف کن» نمی‌شود |
| بدون `:id` | دکمه‌ای که uuid می‌خواهد بی‌فایده است |
| برچسب ≤ ۲۸ کاراکتر + ایموجی | روی گوشی جا شود |
| همیشه یک «🏠 منو» | هیچ‌وقت گیر نمی‌کنی |
| اگر مدل نبود | همان دکمه‌ها به‌صورت آفلاین ساخته می‌شوند |

نمونهٔ واقعی (خروجی تست):

```
بفرما، ۲ مورد پیدا کردم:
۱. شنبه — از 09:00 تا 18:00 — ظرفیت ۴ نفر
۲. دوشنبه — از 10:00 تا 16:00 — ظرفیت ۲ نفر

[ 🕘 ساعت‌های کاری ] [ 📋 نوبت‌ها ]
[ 🛍 خدمات        ] [ 🏠 منو    ]
```

### چه دستورهایی دارد؟

| ورودی | چه می‌شود |
| --- | --- |
| `/start` یا `/menu` | خوش‌آمد + دکمهٔ همهٔ بخش‌ها |
| `/help` | توضیح کامل امکانات |
| `/id` | شناسهٔ چت (برای `TELEGRAM_ALLOWED_CHAT_IDS`) |
| هر جملهٔ فارسی | همان مسیر `/api/chat` → جواب + دکمه |
| دکمهٔ `f:<بخش>` | توضیح آن بخش + اکشن‌های خواندنش (بدون AI، بدون HTTP) |
| دکمهٔ `a:<اکشن>` | همان اکشن را اجرا می‌کند |
| دکمهٔ `✅ / ❌` | تأیید یا لغو یک نوشتن |

## 🔐 ورود بدون رمز — چه چیزی ممکن است و چه چیزی نه

سؤال رایج: «می‌شود بدون پسورد، با پیامک (OTP) لاگین کرد؟»

### جواب صادقانه: با وب‌هوک‌های فعلی سایت **نه**

از کد پروژهٔ سایت دو چیز قطعی است:

| واقعیت | جای کد |
| --- | --- |
| احراز هویت فقط **HTTP Basic** است (ایمیل + پسورد) | `authenticateWebhook` / `parseBasicAuth` در `lib/webhooks/service.ts` |
| ارسال پیامک **پیاده‌سازی نشده** — فقط سه schema برای provider/template/message هست، بدون route | `lib/webhooks/schema.ts` بخش SMS؛ هیچ `app/api/v1/webhooks/sms/route.ts` وجود ندارد |

پس امروز نه می‌توان کدِ پیامکی فرستاد، نه وب‌هوک راهی برای «ورود با کد» دارد.

### و حتی اگر وجود داشت، برای *ربات* انتخاب بدی است

- سرور نمی‌تواند پیامک بگیرد؛ کد را چه کسی بخواند؟
- نشست OTP چند دقیقه‌ای منقضی می‌شود → اتوماسیون هر چند دقیقه می‌شکند.
- OTP برای «اثبات هویت انسان» است؛ ربات یک هویت ماشینی است.

### کاری که کردیم: ورود بدون رمز، با شماره‌ای که تلگرام خودش تأیید کرده

`TELEGRAM_REQUIRE_IDENTITY=true` را روشن کن:

```
کاربر → دکمهٔ «📱 ارسال شمارهٔ من»
        (تلگرام شمارهٔ تأییدشدهٔ خودش را می‌فرستد)
                ↓
middleware → GET /api/v1/webhooks/users?search=0912…
                ↓
        شماره در «کاربران» سایت هست؟ فعال؟ مسدود نیست؟
                ↓
   ✅ وارد شد (نام + نقش از خودِ سایت می‌آید)   ❌ رد + دلیل فارسی
```

### کد کشور (+98) مشکلی درست نمی‌کند — ولی یک تله داشت که حلش کردیم

تلگرام شماره را به فرمت بین‌المللی می‌فرستد (`+989121234567`). نرمال‌سازی همهٔ این‌ها را یکی می‌کند:

| تلگرام می‌فرستد | نرمال می‌شود به |
| --- | --- |
| `+989121234567` | `09121234567` |
| `989121234567` | `09121234567` |
| `00989121234567` | `09121234567` |
| `+98 912 123 4567` | `09121234567` |
| `+98-912-123-4567` | `09121234567` |
| `۰۹۱۲۱۲۳۴۵۶۷` (ارقام فارسی) | `09121234567` |
| `+982188889999` (تهران) | `02188889999` |
| `+14155551234` (خارجی) | ❌ رد: «فقط شماره‌های ایران» |

**اما تله اینجا بود:** فیلد `search` در وب‌هوک سایت یک «شامل بودنِ رشتهٔ خام» است.
یعنی اگر شماره در دیتابیس `+98912…` یا `0912 000 0001` ذخیره شده باشد، جست‌وجوی `09121234567` **پیدا نمی‌کند**.
(۴ از ۵ فرمت رایج شکست می‌خورد — با تست نشان داده شد.)

پس ورود سه‌مرحله‌ای شد:

1. جست‌وجو با چند املا: `0912…`، `912…`، `+98912…`، `98912…`
2. اگر هیچ‌کدام نزد: اسکن حداکثر ۳ صفحه × ۱۰۰ کاربر و **مقایسهٔ نرمال‌شده** (اینجا فرمت اصلاً مهم نیست)
3. تصمیم فقط با **تساوی دقیق** بعد از نرمال‌سازی — هیچ‌وقت با پیشوند

نتیجهٔ تست زنده با فرمت‌های مختلف دیتابیس:

```
تلگرام +98  → دیتابیس 09120000001     ✅ «خوش آمدی دکتر نازنین (admin)»
تلگرام 0098 → دیتابیس +989120000002   ✅ «خوش آمدی منشی با فرمت +98»
تلگرام +98  → دیتابیس 0912 000 0003   ✅ «خوش آمدی کارمند با فاصله»
حساب غیرفعال                           ❌ «حساب تو غیرفعال است»
+14155551234                           ❌ «این شماره ایرانی نیست»
+989120000099                          ❌ «این شماره در فهرست کاربران کلینیک نیست»
```

> هزینه‌اش: در بدترین حالت ۳ درخواست اضافه، فقط یک‌بار در زمان ورود. صفر درخواست در استفادهٔ روزمره (هویت ۱۲ ساعت کش می‌شود).

چرا این امن است:

| نکته | چرا |
| --- | --- |
| شماره را تلگرام تأیید کرده | همان پیامکی که هنگام ساخت اکانت فرستاده شد؛ ما دوباره نمی‌فرستیم |
| `contact.user_id === from.id` | کارت مخاطبِ **فوروارد‌شده** رد می‌شود؛ کسی نمی‌تواند خودش را جای دیگری جا بزند |
| تصمیم با دادهٔ سایت است | مجوز را `users` سایت می‌دهد، نه یک لیست محلی |
| غیرفعال/مسدود | `isActive:false` و `isBanned:true` رد می‌شوند |
| ۱۲ ساعت اعتبار | بعد از آن دوباره باید شماره بفرستد؛ `/logout` هم دستی قفل می‌کند |
| قبل از ورود | هیچ درخواستی به دادهٔ کلینیک نمی‌رود (تست شده) |

دستورها: `/whoami` (من چه کسی هستم؟) و `/logout`.

> ⚠️ این «هویتِ انسان» است. خودِ واسط هنوز برای حرف زدن با وب‌هوک‌ها به یک **هویت ماشینی** نیاز دارد (همان `WEBHOOK_USERNAME/PASSWORD` یا توکن سرویس). هیچ‌وقت پسورد را در کلاینت نگذار.

### اگر واقعاً OTP می‌خواهی، سایت باید این را اضافه کند

سه route تازه در پروژهٔ سایت (و بعد از آن، فقط یک فایل در اینجا):

```http
POST /api/v1/webhooks/auth/otp/request   { "phone": "0912…" }        → 200 { expiresIn: 120 }
POST /api/v1/webhooks/auth/otp/verify    { "phone": "…", "code": "123456" }
                                          → 200 { "token": "...", "expiresAt": "...", "user": { … } }
POST /api/v1/webhooks/auth/refresh       { "token": "..." }           → تازه‌سازی توکن (برای اتوماسیون بلندمدت)
```

و بعد در این پروژه: `lib/webhooks/client.ts` را طوری گسترش می‌دهیم که اگر `WEBHOOK_TOKEN` تنظیم شده باشد، به‌جای Basic از `Authorization: Bearer <token>` استفاده کند (یک‌جا، همهٔ ۴۹ اکشن). این مسیر برای *ربات* درست است: token با عمر بلند + قابل باطل‌کردن، نه OTP کوتاه.

تا آن روز، امن‌ترین ترکیب عملی:

1. یک کاربر سرویس مخصوص ربات بساز، فقط با دسترسی‌های لازم (مثلاً `appointments.read` برای گزارش‌گیری).
2. پسوردش را در env ورمز Vercel بگذار و دوره‌ای عوضش کن.
3. `npm run doctor` را بعد از هر تغییر اجرا کن — اگر پسورد عوض شد، فوراً `401` می‌دهد.

### امنیت

- **`TELEGRAM_WEBHOOK_SECRET`**: تلگرام آن را در هدر `X-Telegram-Bot-Api-Secret-Token` برمی‌گرداند؛ بدون آن `401`.
- **`TELEGRAM_ALLOWED_CHAT_IDS`**: اگر پر باشد فقط همان چت‌ها می‌توانند ربات را کنترل کنند. خالی = هر کسی که ربات را پیدا کند (فقط برای تست).
- **تکرار آپدیت**: `update_id` در حافظه ثبت می‌شود، و همیشه `200` برمی‌گردانیم تا تلگرام یک نوبت را دو بار نسازد.
- نوشتن‌ها همان کارت تأیید را دارند؛ دکمهٔ «بله» همان توکن یک‌بارمصرف را مصرف می‌کند.

## ایمنی و کنترل

۶ قفلِ سخت، که هیچ‌کدام به رفتار مدل وابسته نیست:

1. **منیفست بستهٔ اکشن‌ها** — مدل فقط می‌تواند `bookings.list` را انتخاب کند؛ «آدرس» و «متد» و «دسترسی» در کد نوشته شده. مدل نمی‌تواند URL بسازد.
2. **کارت تأیید** — هر نوشتن/حذف اول «اجازه می‌دهی؟» می‌پرسد. تأییدیه: تک‌بارمصرف، ۱۰ دقیقه اعتبار، **به همان sessionId گره خورده**.
3. **ضدتزریق در ورودی** — `pickAllowed` فقط فیلدهای مجاز اکشن را رد می‌کند؛ `__proto__`, `constructor`, `isAdmin` و هر فیلد ناشناس دور ریخته می‌شود.
4. **اعتبارسنجی شناسه** — اگر `id` شکل uuid نداشته باشد، به‌جای فراخوانی، سؤال می‌پرسد (مدل uuid از خودش نمی‌سازد).
5. **رمزها هرگز برنمی‌گردند** — در پیش‌نمایش، `password` به `••••••` تبدیل می‌شود؛ لاگر کلیدهای حساس را redact می‌کند.
6. **محافظت از خودِ ربات** — `BOT_API_KEY` + rate limit بر اساس IP.

مجوزها همان مجوزهای پروژهٔ فعلی هستند: ربات با یک «کاربر سرویس» وارد می‌شود؛ هر چه آن کاربر نتواند، ربات هم نمی‌تواند. برای همین بهترین کار این است که به آن کاربر فقط دسترسی‌های لازم را بدهید (مثلاً `appointments.read` برای یک ربات گزارش‌گیر).

  و اینکه **قبل از ورود هیچ داده‌ای از کلینیک خوانده نمی‌شود**

## تشخیص اتصال (doctor)

```bash
npm run doctor
# یا با تنظیمات دستی:
WEBHOOK_BASE_URL=https://nafasbeautyclinic.ir WEBHOOK_USERNAME=... WEBHOOK_PASSWORD=... npm run doctor
```

پنج چیز را چک می‌کند و برای هر کدام نسخهٔ «چه کار کنم» می‌دهد:

1. DNS / TCP:443 / TLS و تاریخ انقضای گواهی
2. آیا مسیر `/api/v1/webhooks/bookings` وجود دارد؟ (`401` = ✅ هست و کلید می‌خواهد، `404` = ❌ مسیر/دامنه اشتباه)

4. **جدول مجوزها**: برای هر بخش یک درخواست خواندن می‌زند و می‌گوید `appointments.read` دارد یا نه — اینجوری دقیقاً می‌فهمی کدام کارها از دست ربات برمی‌آید و کدام نه
5. OpenRouter: کلید + زنده بودن هر مدل زنجیره

> اگر از شبکه‌ای اجرا شود که به سرور دسترسی ندارد (فایروال/جغرافیا)، doctor صادقانه همین را می‌گوید و بقیهٔ بخش‌ها را رد می‌کند — نه اینکه پیام گمراه‌کننده بدهد.


- هیچ دیتابیسی لازم نیست. تنها «حافظه» در RAM است (تأییدیه‌ها + آخرین نوبتِ گفت‌وگو).
- ⚠️ اگر ترافیک زیاد شد و Vercel چند instance بالا آورد، ممکن است تأییدیه در instance دیگری نباشد. راه‌حل: `lib/bot/session.ts` را به Upstash Redis / Vercel KV وصل کن — اینترفیس از قبل async است، پس فقط همان یک فایل عوض می‌شود.

### اسرار را کجا نگه داریم؟

`WEBHOOK_PASSWORD` و `OPENROUTER_API_KEY` فقط در env ورمز Vercel. در کلاینت هیچ‌وقت دیده نمی‌شوند، چون این پروژه هیچ صفحهٔ React ندارد و همهٔ فراخوانی‌ها سمت سرور است.

## نکته‌های تولیدی

**کارهایی که خوب است بعداً اضافه شود:**

1. **حافظهٔ پایدار** (Redis) برای تأییدیه‌ها و تاریخچهٔ گفت‌وگو → پشتیبانی از چند instance.
2. **پشتیبانی از تاریخ‌های فارسی** («نوبت‌های فردا»، «هفتهٔ آینده») → تبدیل به بازهٔ `createdAt`/`slotId`؛ الان فیلتر تاریخ در وب‌هوک‌ها وجود ندارد، پس باید در پروژهٔ فعلی اضافه شود.
3. **جستجوی نام → شناسه**: الان برای `get/update/delete` به uuid نیاز است. قدم بعدی: اسم مشتری را بگیری، با `search` پیدا کنی، و اگر یک نتیجه بود خودکار انتخاب کنی (اگر چند بود، انتخاب کن).
4. **Route پیامک**: schema در پروژهٔ هست، route نیست. با اضافه‌شدن route، فقط یک بلوک به `manifest.ts` اضافه می‌شود و همه‌چیز خودکار کار می‌کند.
5. **محدودسازی به کاربرِ واقعی**: الان `BOT_API_KEY` یک کلید مشترک است. بهتر: هر کارمند کلید خودش را داشته باشد و ربات با همان کاربر وب‌هوک صدا زده شود تا audit log درست دربیاید.
6. **`/api/proxy` را جدی بگیر**: اگر پروژهٔ ورسلی داده‌های حساس می‌گیرد، `BOT_API_KEY` را حتماً پر کن و `ALLOWED_ORIGINS` را روی همان دامنه‌های خودت ببند (نه `*`).
7. **حافظهٔ تلگرام**: تأییدیه‌ها در RAM است؛ اگر چند instance داشته باشی، دکمهٔ «بله» ممکن است به instance دیگری برسد. با Redis درست می‌شود (یک فایل: `lib/bot/session.ts`).
8. **حالت tool-calling**: مدل‌های زنجیرهٔ فعلی `tools` را ساپورت می‌کنند؛ `GET /api/features?shape=tools` تعریف‌ها را می‌دهد. برای دقتِ بیشتر روی پیام‌های چندمرحله‌ای می‌شود همین را جایگزین برنامه‌ریز کرد — ولی برای مدل‌های کوچکِ مجانی، مسیر فعلی (JSON + اعتبارسنجی) پایدارتر است.

## English summary

Backend-only Next.js app for Vercel: a Persian-speaking assistant that maps natural language onto the
clinic project's `/api/v1/webhooks/*` endpoints using **free OpenRouter models** with a fallback chain,
a strict action manifest, a human confirmation step for writes, and a deterministic offline fallback so
the bot still works when the free quota is gone. 49 actions across 10 domains, 29 self-tests with no API
key required, and a mock of the target API for local development.
