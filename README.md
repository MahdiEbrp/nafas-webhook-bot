# nafas chat bot 💬

یک **چت‌بات گفت‌وگومحور** به زبان فارسی. هیچ منوی دکمه‌ای، هیچ وب‌هوکی، هیچ دیتابیسی — فقط:
حرفِ کاربر → مدل → جواب.

پروژه یک بک‌اند Next.js است که روی Vercel دیپلوی می‌شود و از دو راه در دسترس است:

- **تلگرام** — ربات، پیام را می‌خواند و جواب می‌دهد.
- **HTTP** — `POST /api/chat` برای هر اپ یا صفحه‌ای که می‌خواهد چت کند (یک صفحهٔ چتِ ساده هم روی `/` هست).

> نسخهٔ قبلی این مخزن یک واسطِ وب‌هوک برای کلینیک بود. همهٔ آن امکانات حذف شده‌اند؛
> الان فقط گفت‌وگو باقی مانده است.

---

## مسیرِ یک پیام

```
کاربر می‌نویسد
      │
      ▼
 /api/telegram/webhook  ← یا →  POST /api/chat
      │
      ▼
 handleChat()               lib/bot/index.ts
      │  پرامپت سیستم + حافظهٔ گفت‌وگو
      ▼
 OpenRouter (زنجیرهٔ مدل‌های :free)   lib/openrouter/client.ts
      │  اولین مدلی که جواب بدهد برنده است
      ▼
 جواب فارسی + ذخیره در حافظه
```

حافظهٔ گفت‌وگو به‌صورت پیش‌فرض ۲۰ رفت‌وبرگشت اخیر (۴۰ پیام کاربر و ربات) را پیش از پیام جدید به مدل می‌دهد. `HISTORY_MESSAGES` تعداد پیام‌هاست، نه تعداد رفت‌وبرگشت‌ها؛ مقدار صریح محیط بر پیش‌فرض اولویت دارد. دستیار ابزارها نیز تا ۴۰ پیام قبلی را می‌خواند.

حافظه در همان پروسه نگه داشته می‌شود (با TTL پیش‌فرض ۳۰ دقیقه) —
بدون دیتابیس. اگر کاربرِ هم‌زمانِ زیادی داشتی، همین یک فایل
(`lib/bot/session.ts`) را به Upstash/Redis وصل کن. در cold start یا بین instanceهای متفاوت Vercel، این حافظه مشترک یا پایدار نیست. پیام‌های حساس OTP وارد حافظه نمی‌شوند؛ تصمیم‌های امنیتی و تأیید عملیات همچنان توسط کد کنترل می‌شوند.

## هویت و تقویم

**«تو کی هستی؟»** همیشه یک جواب دارد: «من نفَس هستم، دستیار هوشمند کلینیک زیبایی نفس.»
این جواب در `lib/bot/identity.ts` با کد داده می‌شود، نه با پرامپت — چون مدلِ کوچکِ مجانی
گاهی خودش را «یک مدل زبانی» معرفی می‌کند. اسم کلینیک با `CLINIC_NAME` عوض می‌شود.

**تاریخ** سه لایه دارد و همه با `date-fns` کار می‌کنند:

| لایه | فایل | کار |
| --- | --- | --- |
| خواندنِ تاریخ از جمله | `lib/dates/parse.ts` | «۱۲ مرداد ۱۴۰۳»، «1403/05/12»، «2024-08-15»، «15 August 2024»، «امروز»، «پنجشنبه»، «عید»، «۱۴۰۳» |
| محاسبه | `lib/dates/engine.ts` | تبدیل، فاصلهٔ دو تاریخ، رنج روزها، جمع و تفریق زمان، طول ماه، سال کبیسه |
| تصمیم | `lib/dates/intent.ts` | کدام عملیات خواسته شده — و اینکه آیا اصلاً سؤالِ تاریخ است یا نه |

سه تقویم: **شمسی** (`date-fns-jalali`)، **میلادی** (`date-fns`)، **قمری** (`Intl` با
`islamic-umalqura`).

```
«بین 1403/01/01 و 1403/01/10 چند روزه»
   → parse: دو تاریخ پیدا شد
   → engine: differenceInCalendarDays = 9
   → مدل: فقط جمله را می‌نویسد، عدد را دست نمی‌زند
   → اگر عدد را عوض کرد، جوابِ محاسبه‌شده جایگزین می‌شود
```

چهار نکته که عمداً این‌طور طراحی شده‌اند:

1. **محاسبات با کد است، نه با مدل.** مدلِ کوچک تاریخ را از حفظ می‌سازد؛ پس عدد را ما حساب
   می‌کنیم و مدل فقط جمله‌بندی می‌کند. اگر مدل عدد را خراب کند، `summary` محاسبه‌شده
   جایگزین می‌شود.
2. **هرگز خالی نمی‌ماند.** اگر همهٔ مدل‌ها از کار بیفتند، جوابِ تاریخ هنوز درست است.
3. **ساعت از سرور، در منطقهٔ درست.** سرور UTC است و `TIME_ZONE=Asia/Tehran`. یک لحظه در
   UTC می‌شود ۱۴۰۵/۰۸/۱۸ و در تهران ۱۴۰۵/۰۸/۱۹ — پس `@date-fns/tz` لازم است.
4. **جملهٔ معمولی را اشتباه نمی‌گیرد.** «دیروز خیلی خسته بودم» سؤالِ تاریخ نیست؛ یک
   کلمهٔ نسبی به‌تنهایی کافی نیست، باید یا تاریخِ صریح باشد یا کلمهٔ پرسشیِ تاریخ.

**دربارهٔ `date-fns-jalali`:** این یک فورکِ کاملِ date-fns است که کل API را روی تقویم
جلالی اجرا می‌کند. دو چیزی که اندازه‌گیری شد و در کد هم نوشته شده:

- ماه/سال را **حتماً** با نسخهٔ جلالی حساب کن: `addMonths(1403/01/31, +6)` در date-fns
  می‌شود `1403/07/28` (چون شش ماهِ *میلادی* جلو می‌رود) و در نسخهٔ جلالی `1403/07/30` ✓
- تبدیل‌ها روی **۴۸۶۷ روزِ نمونه در ۴۰ سال** با `jalaali-js` مقایسه شد: صفر اختلاف.
  `Intl` با `ca-persian` هم همان ۱۴۰۵/۰۸/۱۸ را می‌دهد.

قاعدهٔ کبیسه، الگوریتمِ حسابیِ ۳۳‌ساله است (مثل خودِ jalaali-js)؛ در برخی سال‌ها ممکن است
یک روز با تقویمِ نجومیِ رسمی اختلاف داشته باشد.

## ذخیرهٔ تنظیمات در دیتابیس

هر **کاربرِ** تلگرام یک `session_id` دارد که در Postgres ذخیره می‌شود: کلید، شناسهٔ
کاربری تلگرام است و مقدار، همان session.

**کلید، user id است نه chat id** — تا رکورد به خودِ آدم بچسبد: با چتِ تازه از بین نرود،
و در گروه همهٔ اعضا یک ردیف مشترک نداشته باشند. برای فرستادنِ پاسخ همچنان از chat id
استفاده می‌شود؛ این دو فقط در چتِ خصوصی عددِ یکی هستند.

جدول‌هایی که قبلاً با `telegram_chat_id` ساخته شده‌اند خودکار rename می‌شوند و داده‌شان
سالم می‌ماند (در چتِ خصوصی، chat id و user id یک عدد بوده‌اند).

| فایل | کار |
| --- | --- |
| `lib/db/client.ts` | اتصال به Neon با درایور HTTP خودِ Neon؛ تعمیرِ رشتهٔ اتصال؛ timeout |
| `lib/db/schema.ts` | جدول `chat_sessions` — idempotent، پس هر بار می‌تواند اجرا شود |
| `lib/db/chat-sessions.ts` | upsertِ «کلید → session» + کش در حافظهٔ پروسه |

```sql
create table if not exists chat_sessions (
  telegram_user_id bigint      primary key,   -- همان key که خواستی
  session_id       text        not null,      -- همان session
  phone            text,                      -- موبایل ایران، به شکل 09121234567
  created_at       timestamptz not null default now(),
  updated_at       timestamptz not null default now(),
  last_seen_at     timestamptz not null default now()
);
```

جدول‌هایی که **قبل از** ستون `phone` ساخته شده‌اند خودکار عریض می‌شوند
(`alter table … add column if not exists`)، پس نیازی به migration دستی نیست.

سه تصمیم:

1. **دیتابیس یک وابستگی نیست، یک افزونه است.** اگر `DATABASE_URL` خالی باشد یا Neon
   نرسد، بات دقیقاً مثل قبل کار می‌کند و session را از `tg-<chatId>` می‌سازد. پیامِ کاربر
   هیچ‌وقت به خاطر دیتابیس از دست نمی‌رود.
2. **یک upsert، نه select-بعد-insert.** با `(xmax = 0) as inserted` در همان `RETURNING`
   می‌فهمیم چت تازه بوده یا نه — بدون کوئری دوم.
3. **کش در حافظهٔ پروسه.** session یک چت هیچ‌وقت عوض نمی‌شود، پس بعد از اولین پیام، آن
   چت دیگر به دیتابیس دست نمی‌زند. عمداً شمارندهٔ پیام نگذاشتم: به‌روزش نیازمندِ یک write
   روی هر پیام بود و روی serverless آن write تضمین‌شده نیست — ستونی که گاهی دروغ می‌گوید
   از نبودنش بدتر است.

`newSessionId()` در `lib/db/chat-sessions.ts` **تنها** جایی است که session ساخته می‌شود.
وقتی گفتی session از کجا باید بیاید، فقط همان یک تابع عوض می‌شود.

## شمارهٔ تلفن

تا وقتی شمارهٔ موبایل یک **کاربر** در دیتابیس نباشد، **هیچ پیامی جواب داده نمی‌شود**.
بات یک بار شماره را می‌خواهد و بعد همه‌چیز عادی است. چون کلید user id است، شماره‌ای که
در یک چت داده‌ای در چتِ دیگر هم معتبر است.

به‌روزرسانی‌هایی که `from` ندارند (پستِ کانال، ادمینِ ناشناس گروه) رد می‌شوند: کاربری وجود
ندارد که چیزی به نامش ثبت شود، و حدس‌زدنِ chat id یعنی قاطی‌شدنِ رکوردِ چند غریبه.

شماره از خودِ تلگرام می‌آید: یک دکمهٔ `request_contact` زیر کادر پیام می‌نشیند و کاربر با
یک ضربه شمارهٔ حساب تلگرامش را می‌فرستد (`message.contact`)، نه چیزی که تایپ کرده باشد.
اگر دکمه را نزند، می‌تواند شماره را تایپ کند.

| فایل | کار |
| --- | --- |
| `lib/phone.ts` | خواندن و نرمال‌سازی شماره؛ تنها جایی که قاعدهٔ «فقط ایران» هست |
| `lib/telegram/phone-gate.ts` | خودِ gate: پرسیدن، گرفتن، رد کردن، تأیید |
| `lib/telegram/api.ts` | `contactKeyboard()` و `removeKeyboard()` |

قاعدهٔ ذخیره: **`09XXXXXXXXX` — یازده رقم، بدون کد کشور.** همهٔ شکل‌ها به همین یک شکل
تبدیل می‌شوند:

| ورودی | ذخیره می‌شود |
| --- | --- |
| `۰۹۱۲۱۲۳۴۵۶۷` (رقم فارسی) | `09121234567` |
| `+989121234567` / `00989121234567` | `09121234567` |
| `989121234567` | `09121234567` |
| `9121234567` (بدون صفر) | `09121234567` |
| `0912-123-4567` / `(0912) 123 4567` | `09121234567` |
| `+14155552671` / `02112345678` | رد می‌شود |

سه نکته:

1. **`/start` هم پشت gate است** — خوش‌آمدگویی قبل از شماره داده نمی‌شود. تنها استثنا
   `/id` است: چیزی ذخیره نمی‌کند و تنها راهِ فهمیدنِ chat id برای
   `TELEGRAM_ALLOWED_CHAT_IDS` است؛ بستنش یعنی بن‌بست.
2. **در گروه‌ها دکمهٔ اشتراک شماره وجود ندارد** (محدودیت خودِ تلگرام)، پس بات در گروه
   شماره را به‌صورت متنی می‌خواهد.
3. **بدون دیتابیس، gate کنار می‌رود.** جایی برای ذخیرهٔ شماره نیست و پرسیدنِ بی‌پایان
   یعنی بات برای همه از کار افتاده — پس مثل قبل جواب می‌دهد. `PHONE_GATE=off` هم gate را
   خاموش می‌کند در حالی که ذخیره‌سازی سر جایش می‌ماند.

```bash
npm run db:check                       # اتصال + ساخت جدول + رفت‌وبرگشتِ واقعی
curl -s https://<your-app>/api/health?db=1
```

## کلاینت مدیریت قوانین

`RuleManager` در `lib/rules/manager.ts` یک کلاینت برای **API بیرونی** قوانین است؛ این مخزن endpoint یا داشبورد قوانین پیاده نمی‌کند. origin پیش‌فرض `https://nafasbeautyclinic.ir` است و با `NAFAS_API_BASE_URL` یا گزینهٔ `baseUrl` قابل تنظیم است؛ `RULES_API_BASE_URL` هم برای override اختصاصی قوانین پشتیبانی می‌شود. برای دادهٔ دامی در تست، صریحاً `new RuleManager({ baseUrl: "" })` بساز. درخواست زنده فقط روی HTTPS فرستاده می‌شود.

```ts
import { RuleManager } from "@/lib/rules/manager";
import type { RuleRequestContext } from "@/lib/rules/types";

const rules = new RuleManager({ baseUrl: process.env.RULES_API_BASE_URL });
// این context را فقط از لایهٔ احراز هویت قابل‌اعتماد بگیر؛ نه از متن چت.
const auth: RuleRequestContext = {
  actorId: authenticatedActor.id,
  sessionCookie: authenticatedRequest.cookieHeader,
  csrfToken: authenticatedRequest.csrfToken,
};
const page = await rules.list({ page: 1, perPage: 10, status: "active" }, auth);
const proposal = await rules.proposeDelete(ruleId, auth);
if (proposal.ok) {
  // تغییر تنها پس از تأیید صریح همان actor ارسال می‌شود.
  const result = await rules.confirm(proposal.change.token, auth);
}
```

اعتبارسنجی‌های ورودی همان محدودیت‌های قرارداد Rules API را اعمال می‌کنند: slug به‌شکل kebab-case و حداکثر ۱۶۰ نویسه؛ نام fa/en از ۱ تا ۲۵۶؛ توضیح تا ۲۰۰۰؛ icon تا ۱۰۰، image تا ۲۰۴۸ و color تا ۵۰؛ displayOrder از ۰ تا ۱۰۰۰۰؛ صفحه ۱ تا ۱۰۰۰۰۰ و perPage از ۱ تا ۱۰۰؛ جست‌وجو تا ۱۰۰ نویسه؛ و bulk با حداکثر ۱۰۰ UUID در scope=`page` یا فقط search/status در scope=`filtered`. پیش‌فرض‌ها `highlighted=false`، `displayOrder=0` و `isActive=true` هستند. PATCH فقط فیلدهای داده‌شده را می‌فرستد و ترجمه‌های fa/en را مستقل نگه می‌دارد.

مسیرهای مورد انتظار: `GET/POST /api/v1/rules`، `GET/PATCH/DELETE /api/v1/rules/:id` و `POST /api/v1/rules/bulk`. کلاینت status و `x-request-id` را به فراخواننده منتقل می‌کند. API مقصد باید خودش مجوزهای `rules.read` برای GET، `rules.write` برای POST/PATCH و `rules.manage` برای DELETE، session-cookie، CSRF، rate limit، audit event حذف (`action: "deleted"`, `entityType: "rule"`) و header `x-request-id` را اجرا/ثبت کند؛ کلاینت این کنترل‌های سمت سرور را جایگزین نمی‌کند.

Cookie و CSRF هر دو به‌صورت context **برای هر فراخوانی** داده می‌شوند و داخل manager یا `RULES_API_BASE_URL` ذخیره نمی‌شوند. تأیید به `actorId` پیشنهاددهنده بسته است و فراخوانی با کاربر دیگر رد می‌شود. مقدارهای cookie/token را در log یا env مشترک نگذار.

برای اتصال کتابخانه به مدل، `RulesAssistant` در `lib/rules/assistant.ts` از function calling در OpenRouter استفاده می‌کند و `handleChat` هم می‌تواند به‌صورت اختیاری آن را دریافت کند:

```ts
import { handleChat } from "@/lib/bot";
import { RulesAssistant } from "@/lib/rules/assistant";

const rulesAI = new RulesAssistant({ manager: apiRules }); // یک instance مشترک در محدودهٔ اجرای میزبان
const answer = await handleChat({
  message,
  sessionId: conversationId,
  locale: "fa",
  rulesAssistant: rulesAI,
  ruleContext: authenticatedContext, // فقط از adapter احراز هویت معتبر
});
```

مدل برای خواندن از ابزارهای `list_rules` و `get_rule` و برای تغییر از `create_rule`، `update_rule`، `delete_rule` و `bulk_rules` استفاده می‌کند. خواندن پس از مجوزسنجی API انجام می‌شود؛ هر تغییر ابتدا proposal است و فقط جواب روشن «تأیید» یا «لغو» به‌صورت قطعی پردازش می‌شود، نه برداشت مدل از موافقت مبهم. محتوای API به مدل می‌رود تا پاسخ خواندنی بسازد، اما cookie و CSRF هرگز به مدل فرستاده نمی‌شوند. مدل انتخاب‌شده باید از function calling پشتیبانی کند. پاسخ «چه کارهایی بلدی؟» همیشه توانایی‌های قوانین را هم فهرست می‌کند و اگر context معتبر تزریق نشده باشد، روشن می‌گوید که این قابلیت در مسیر پیش‌فرض فعال نیست.

مسیر `/api/chat` عمداً auth context قوانین تزریق نمی‌کند، چون شناسهٔ session مرورگر به‌تنهایی هویت قابل‌اعتماد نیست. در Telegram، ورود پیامکی فقط در گفت‌وگوی خصوصی فعال است؛ بعد از OTP معتبر، context هر درخواست از نشست رمز‌شدهٔ همان کاربر بارگذاری می‌شود. proposalها و توکن‌های تأیید قوانین همچنان در حافظهٔ instance نگهداری می‌شوند؛ در استقرار چندنمونه‌ای یا serverless، برای تأیید بین درخواست‌ها باید میزبان عمر instance را تضمین کند یا ذخیره‌ساز پایدار اضافه شود. فیلد `icon` نام export آیکون `lucide-react` را به‌صورت رشته نگه می‌دارد؛ اگر UI ساخته شد، آن را با نگاشت/allowlist ثابت به کامپوننت تبدیل کن، نه import پویا از مقدار API.

| فایل | کار |
| --- | --- |
| `lib/rules/types.ts` | مدل‌ها، context احراز هویت و نتیجه‌ها |
| `lib/rules/manager.ts` | کلاینت HTTP، دادهٔ دامی و پیشنهاد/تأیید تغییرها |
| `lib/rules/assistant.ts` | ابزارهای function-calling هوش مصنوعی و گردش تأیید |
| `scripts/selftest.ts` | تست‌های آفلاین اعتبارسنجی، مرز احراز هویت و درخواست‌های API |

## ورود پیامکی OTP به API نفس

کلاینت `SmsOtpClient` در `lib/auth/sms-otp.ts` برای سرویس `https://nafasbeautyclinic.ir` سه درخواست `request`، `verify` و `resend` را می‌فرستد. شماره با قالب عمومی ۷ تا ۱۵ رقم و `+` اختیاری پذیرفته می‌شود؛ کد تأیید دقیقاً ۶ رقم ASCII است. حساب باید از قبل در سامانه با همان شماره فعال و غیرمسدود باشد؛ این کلاینت ثبت‌نام یا رمز عبور ندارد.

در ربات Telegram و فقط در گفت‌وگوی خصوصی، کاربر می‌تواند به زبان طبیعی بنویسد «می‌خواهم لاگین کنم» یا “I want to log in”. ربات شماره را می‌پرسد، کد پیامک را می‌گیرد و پس از تأیید، context احراز هویت را به دستیار AI قوانین وصل می‌کند. شماره و کد در این گردش به OpenRouter یا تاریخچهٔ چت فرستاده نمی‌شوند. وضعیت موقت ورود تا ۱۰ دقیقه در جدول `auth_login_flows` رمز‌شده نگهداری می‌شود. پاسخ «چه کارهایی بلدی؟» در Telegram هم ورود پیامکی را به‌عنوان قابلیت فهرست می‌کند. مسیر وب `/api/chat` عمداً این هویت را نمی‌پذیرد.

```ts
import { SmsOtpClient } from "@/lib/auth/sms-otp";

const otp = new SmsOtpClient(); // NAFAS_API_BASE_URL یا https://nafasbeautyclinic.ir
const sent = await otp.request("09121234567");
// کاربر کد پیامک‌شده را وارد می‌کند.
const verified = await otp.verify("09121234567", code);
if (verified.ok && verified.ruleContextAvailable) {
  // نشست از DB رمزگشایی می‌شود؛ فقط server-side استفاده کن و به مدل/log نده.
  const context = await otp.getRuleRequestContext("09121234567");
  if (context) await rulesAssistant.handle({ conversationId, message, context });
}
```

`resend(phone)` همان بدنهٔ درخواست را به مسیر resend می‌فرستد. مقدارهای `expiresInMs` و `resendInMs` از پاسخ سرور خوانده می‌شوند؛ محدودیت ۵ درخواست در ۱۵ دقیقه برای IP و ۵ در ۵ دقیقه برای شماره باید توسط API مقصد اعمال شود و کلاینت آن‌ها را دور نمی‌زند. پاسخ verify می‌تواند Set-Cookie و CSRF header `x-csrf-token` داشته باشد. اگر CSRF در cookie برمی‌گردد، نامش را با `csrfCookieName` تنظیم کن. بدون cookie و CSRF، `ruleRequestContext` ساخته نمی‌شود؛ API contract ارسالی این جزئیات را تضمین نکرده بود، پس کلاینت حدس نمی‌زند.

شماره و کد در log نوشته نمی‌شوند. پس از verify، cookie و CSRF فقط به شکل AES-256-GCM ciphertext در جدول `auth_sessions` ذخیره می‌شوند؛ actor lookup با HMAC انجام می‌شود تا شماره در ستون‌های دیتابیس آشکار نباشد. برای این مسیر، `DATABASE_URL` و کلید مستقل ۳۲‌بایتی `AUTH_SESSION_ENCRYPTION_KEY` الزامی‌اند؛ کلید را با `openssl rand -hex 32` بساز، در secret manager نگه دار و بین deployها ثابت نگه‌دار. بدون DB یا کلید معتبر، ذخیره‌سازی fail-closed است و verify موفقیت‌آمیز گزارش نمی‌شود. نشست حداکثر ۷ روز و در صورت وجود expiry کوتاه‌تر کوکی، تا همان زمان نگهداری می‌شود. با `getRuleRequestContext(lookupId)` context از DB بازیابی می‌شود؛ در استفادهٔ مستقیم، lookupId همان شماره است و adapter تلگرام آن را به شناسهٔ پایدار کاربر محدود می‌کند. `clearStoredSession(lookupId)` رکورد محلی را حذف می‌کند (این حذف نشست را در سرویس upstream revoke نمی‌کند). نشست خام را به مدل یا log نفرست. ورود OTP از phone-gate تلگرام مستقل است و در صورت معتبر بودن context احراز‌شده می‌تواند phone gate را برآورده کند.

| فایل | کار |
| --- | --- |
| `lib/auth/sms-otp.ts` | کلاینت OTP و بازیابی server-side context نشست از store رمز‌شده |
| `lib/auth/session-store.ts` | ذخیرهٔ AES-256-GCM نشست در Postgres با lookup مبتنی بر HMAC |
| `lib/auth/login-flow-store.ts` | نگهداری رمز‌شدهٔ کوتاه‌مدت phone/code stage برای ورود Telegram |

## مدیریت کاربران

یک کلاس، `UserManager` در `lib/users/manager.ts`. ساخت حساب، جست‌وجو (نام، ایمیل، شماره یا UUID)، ویرایش، حذف نرم، فعال/غیرفعال، مسدودسازی و رفع مسدودی، تغییر رمز و بازنشانی رمز.

قواعد محلی ساخت حساب بر اساس مقاله:

- `fullName`: پس از trim، بین ۲ تا ۱۰۰ نویسه.
- `email`: قالب ایمیل، پس از trim حروف کوچک، حداکثر ۲۵۴ نویسه.
- `phone`: ۷ تا ۱۵ رقم با `+` اختیاری در ابتدا.
- رمز: ۸ تا ۱۲۸ نویسه و شامل حرف کوچک، حرف بزرگ، عدد و نشانه.
- کلیدهای نقش پیش‌فرض: `admin`، `doctor`، `receptionist` یا `customer`؛ برای نقش‌های سفارشی، کلیدهای فعلی جدول نقش‌ها را با `roleKeys` به کلاس بده.
- شناسهٔ هدف در تغییرات: UUID.

رمز حساب جدید و رمز تغییر‌یافته فقط در حافظهٔ خصوصیِ پیشنهادِ منتظرِ تأیید می‌ماند و در خلاصه، لاگ یا رکورد دامی قرار نمی‌گیرد؛ API تنها بعد از تأیید آن را دریافت می‌کند. رمز موقتِ پاسخ reset فقط به فراخواننده برمی‌گردد—آن را به مدل یا لاگ نفرست. هر درخواست زنده نیازمند Basic Auth هویتِ مدیر است. کلاس بدون ایمیل و رمزِ همان درخواست‌کننده، اصلاً درخواست HTTP نمی‌فرستد.

| فایل | کار |
| --- | --- |
| `lib/users/types.ts` | فقط تایپ‌ها |
| `lib/users/manager.ts` | خودِ کلاس |
| `lib/users/capabilities.ts` | فهرست توانایی‌ها — هم برای تست، هم برای پاسخِ بات |
| `lib/users/intent.ts` | تشخیصِ «چه کارهایی بلدی؟» |

### دادهٔ دامی تا وقتی که آدرس نداده‌ای

بدون `baseUrl` کلاس روی یک حافظهٔ کوچک با سه کاربرِ نمونه کار می‌کند، پس همین امروز
قابل استفاده و تست است. `baseUrl` بدهی همان متدها به HTTP می‌روند و هیچ فراخوانی‌ای
عوض نمی‌شود.

```ts
const dummyUsers = new UserManager(); // دادهٔ دامی

// نمونه: یک instance برای درخواست‌کنندهٔ احراز هویت‌شده؛ رمز را به مدل یا لاگ نده.
const apiUsers = new UserManager({
  baseUrl: process.env.USERS_API_URL,
  credentials: { email: authenticatedActor.email, password: authenticatedActor.password },
});
```

### مرز مسئولیت‌ها با API حساب

این مخزن پیاده‌سازی جدول `users`، جدول‌های `roles`، احراز رمز با Argon2 یا مسیرهای مدیریت حساب را ندارد؛ بنابراین کلاس فقط به API بیرونی درخواست می‌فرستد. API مقصد باید در سمت سرور (نه با اعتماد به این کلاس) همهٔ کنترل‌های امنیتی مقاله را اجرا کند: بررسی Basic Auth و وضعیت/حذف حساب، مجوزهای `users.manage` و `users.write` و `assertCanGrantRole`، یکتایی ایمیل و وجود نقش، جلوگیری از self-lockout و حذف آخرین مدیر فعال، ثبت soft-delete، ابطال نشست در deactivate/ban/reset، تولید رمز موقت و اجبار به تغییر آن، و محدودیت ۳۰ درخواست در ساعت با کلید `webhook:user:<userId>`. این کلاس آرگومان‌های ورودی را اعتبارسنجی می‌کند و پاسخ‌های HTTP مانند 401/403/404/409/429 را منتقل می‌کند؛ به‌تنهایی جای کنترلِ سمت سرور را نمی‌گیرد.

قرارداد مسیرهای HTTP موجود در کلاس (`/users`, `/users/:id`, `/users/:id/password`, `/users/:id/reset-password`, `/users/bulk`) فعلاً فرضی است، چون نشانی/قرارداد API واقعی هنوز ارائه نشده است. پس از دریافت قرارداد واقعی باید مسیرها و شکل بدنه‌ها با آن تطبیق داده شوند.

### هیچ تغییری بدون تأیید ارسال نمی‌شود

این قاعده شکلِ API را ساخته، پس هر تغییر **دو مرحله** دارد:

```ts
const proposal = await users.proposeBulk([
  "11111111-1111-4111-8111-111111111001",
  "11111111-1111-4111-8111-111111111002",
], "disable");
// تا اینجا هیچ درخواستِ تغییری ارسال نشده — فقط یک توکن و یک توضیح

const result = await users.confirm(proposal.change.token);
// حالا ارسال شد
```

سه نکته:

1. `propose…` فقط **می‌خواند** (تا مطمئن شود کاربر وجود دارد) و هرگز درخواست تغییر نمی‌زند. این را تست روی خودِ درخواست‌ها بررسی می‌کند، نه روی مقدار بازگشتی.
2. توکن **یک‌بارمصرف** است؛ `confirm` دوم `unknown-token` می‌گیرد.
3. توکن **منقضی می‌شود** (پیش‌فرض ۵ دقیقه). در چت، پیشنهادی که فراموش شده نباید یک ساعت
   بعد با یک «بله» که برای چیز دیگری بوده اجرا شود.

### چه کارهایی بلدی؟

فهرست توانایی‌ها در `capabilities.ts` نوشته شده و **یک جا** است: تست‌ها از رویش
برمی‌دارند و بات هم. پس پاسخِ «چه کارهایی بلدی؟» هیچ‌وقت از کد عقب نمی‌ماند. همان فهرست
به system prompt هم تزریق می‌شود تا مدل چیزی را که کلاس بلد نیست ادعا نکند. کارهایی که
داده را عوض می‌کنند با 🔒 علامت خورده‌اند و بات قول می‌دهد قبلشان تأیید بگیرد.

### پوششِ تست

`npm run coverage` این ماژول را روی **۱۰۰٪** در هر چهار معیار (statements, branches,
functions, lines) نگه می‌دارد و در CI هم اجرا می‌شود. `types.ts` مستثناست چون فقط
تعریفِ تایپ است و به کدِ اجرایی ترجمه نمی‌شود.

## انتخابِ خودکارِ مدل

بات مدل را دستی انتخاب نمی‌کند؛ هر بار **بهترین مدلِ مجانیِ در دسترس** را از فهرست
زندهٔ OpenRouter برمی‌دارد. سه سیگنال دارد:

| سیگنال | از کجا | چرا |
| --- | --- | --- |
| **کیفیت** | جدولِ دستیِ `QUALITY_TIERS` در `lib/openrouter/ranking.ts` | API اوپن‌روتر هیچ نمرهٔ هوشی نمی‌دهد، پس قضاوتِ ما باید یک‌جایی نوشته شود |
| **سرعت** | اندازه‌گیریِ واقعیِ خودِ بات (`lib/openrouter/stats.ts`) | API هیچ latency هم نمی‌دهد؛ تنها عددِ واقعی، زمانِ جواب‌های خودمان است |
| **سلامتی** | cooldown بعد از خطا | مدلی که ۴۲۹ می‌دهد باید برود عقبِ صف، نه اینکه حذف شود |

```
فهرست زندهٔ :free → فیلتر زمینه → نمرهٔ کیفیت + سرعت − cooldown → N مدلِ اول
```

سه قانون که نگهشان داشته‌ام:

1. **هرگز خالی نمی‌شود.** اگر فهرست زنده گرفته نشد، به `OPENROUTER_MODELS` برمی‌گردد.
   باتِ بی‌حرف بهتر از باتِ کم‌حرف نیست.
2. **حذف نمی‌کند، فقط عقب می‌فرستد.** مدلِ خطاداد بعد از `MODEL_COOLDOWN_MS` برمی‌گردد.
3. **همیشه کاوش می‌کند.** یک جایِ استخر به مدلی که هنوز زمانش را نگرفته‌ایم می‌رسد،
   وگرنه اولین مدلی که جواب داد تا ابد «سریع‌ترین» می‌ماند.

**یک نکتهٔ صادقانه:** «سریع‌ترین» و «باهوش‌ترین» معمولاً دو مدلِ متفاوت‌اند
(مدل‌های مجانیِ باهوش کندترند). پس وزنِ سرعت عمداً کمتر از فاصلهٔ بین رده‌های کیفیت است:
کیفیت رده را تعیین می‌کند و سرعت فقط بین مدل‌های هم‌رده تصمیم می‌گیرد.
اگر اولویتت سرعت است، `QUALITY_TIERS` را ویرایش کن یا `MODEL_SELECTION=fixed` بگذار.

```bash
npm run models      # رتبه‌بندیِ زنده + زنجیره‌ای که بات الان راه می‌رود
curl -s https://<your-app>/api/health   # همان، به‌همراهِ سرعت‌های اندازه‌گیری‌شده
```

| `ALLOWED_ORIGINS` | چه دامنه‌هایی از مرورگر اجازهٔ صدا زدن دارند |
| `TELEGRAM_BOT_TOKEN` / `TELEGRAM_WEBHOOK_SECRET` / `PUBLIC_APP_URL` | وصل شدن به تلگرام |
| `TELEGRAM_ALLOWED_CHAT_IDS` | فقط این چت‌ها بتوانند با بات حرف بزنند |

## دستورها در تلگرام

| دستور | کار |
| --- | --- |
| `/start` | سلام دوباره |
| `/help` | بات چیست و چه می‌کند |
| `/clear` (`/reset`, `/new`) | فراموش کردن گفت‌وگو و شروع تازه |

## API

```bash
curl -X POST https://<your-app>/api/chat \
  -H 'Content-Type: application/json' \
  -H 'x-bot-key: <BOT_API_KEY>' \
  -d '{"message":"سلام، حالت چطوره؟","sessionId":"demo"}'
```

```json
{
  "ok": true,
  "data": {
    "status": "answered",
    "reply": "سلام! خوبم، تو چطوری؟ 🙂",
    "model": "liquid/lfm-3-1.7b:free",
    "ms": 812,
    "contextMessages": 2,
    "truncated": false,
    "sessionId": "demo"
  }
}
```

`status` یکی از `answered | empty | error` است. بات وقتی مدل جواب نمی‌دهد
**حدس نمی‌زند**؛ `error` برمی‌گرداند و از کاربر می‌خواهد دوباره تلاش کند.

مسیرهای دیگر: `GET /api/health`، `GET|POST /api/telegram/setup`.

### مدیریت کاربران تلگرام مطابق API کلینیک

قرارداد مرجع: `MahdiEbrp/beauty-clinic`، commit
`af5d4f872a7ac8f75fa1e6780e788e83557c5100` (main).
اعتبارسنجی از `lib/validation/user.ts` و مسیرهای `app/api/v1/users` تطبیق داده شده است.

در خصوصی وارد حساب مجاز شو، سپس «کاربر جدید بساز» را بفرست. ربات نام کامل،
ایمیل، تلفن، رمز و کلید نقش را مرحله‌به‌مرحله می‌گیرد؛ رمز و مشخصات به مدل یا
تاریخچه فرستاده نمی‌شوند. برای راهنمای همهٔ فرمان‌ها `/users help` را بفرست.

| فرمان | API |
|---|---|
| `/users list {"page":1,"perPage":10,"status":"all"}` | GET /api/v1/users؛ جست‌وجو و فیلتر نقش/وضعیت |
| `/users create {…}` | POST /api/v1/users |
| `/users status UUID {"isActive":false}` | PATCH /api/v1/users/:id |
| `/users status UUID {"isBanned":true,"banReason":"…"}` | مسدودسازی؛ false برای رفع مسدودی |
| `/users role UUID {"roleKey":"…"}` | PATCH /api/v1/users/:id/role |
| `/users password UUID {"password":"…","confirmPassword":"…"}` | POST /api/v1/users/:id/password |
| `/users delete UUID` | DELETE /api/v1/users/:id (حذف نرم) |
| `/users bulk {"action":"activate","scope":"page","ids":["UUID"]}` | POST /api/v1/users/bulk |

عملیات گروهی: activate، deactivate، ban، unban، change-role (با roleKey)، delete،
reset-password. برای scope=filtered از filters شامل search/status/role استفاده کن.
تعداد شناسه‌های صفحه حداکثر ۱۰۰ است. عملیات تغییردهنده فقط پس از «تأیید» اجرا
می‌شوند؛ «لغو» پیشنهاد را حذف می‌کند. تأیید یک‌بارمصرف، وابسته به مالک و نشست
و با مهلت پنج دقیقه است. پیشنهادها در حافظهٔ process هستند و بین instanceها یا
cold start پایدار نیستند؛ در این حالت باید درخواست را از ابتدا شروع کرد.

کلاینت تنها به HTTPS، با کوکی نشست همان درخواست‌کننده و Origin مقصد درخواست
می‌فرستد؛ redirect و retry خودکار ندارد. API مرجع CSRF را با تطبیق Origin و
Host کنترل می‌کند و پاسخ موفق آن `{data: ...}` است، نه `ok: true`.
کنترل permissions، نقش‌های مجاز و جلوگیری از self-lockout همچنان در سرویس
مرجع اعمال می‌شود؛ ورود موفق به معنی داشتن مجوز مدیریت کاربران نیست.
رمزهای موقت reset فقط مستقیماً در گفت‌وگوی خصوصی برگردانده می‌شوند؛ آن‌ها را
منتشر نکن. نگهداری رمز در پیام‌های خود تلگرام با حافظهٔ مدل متفاوت است؛ برای
حساب‌های حساس از پنل امن کلینیک استفاده کن.

**محدودیت قرارداد مرجع:** تغییر نام/ایمیل/تلفن و GET تکی کاربر endpoint ندارند؛
ربات آن‌ها را اختراع نمی‌کند. مسیر قدیمی AI برای تغییر کاربران غیرفعال شده و
درخواست‌های تغییردهنده باید از جریان خصوصی `/users` انجام شوند.

تست‌ها از fetch ساختگی استفاده می‌کنند؛ تست روی دادهٔ واقعی یا deploy انجام نشده است.

### قالب پیام‌های تلگرام

پیام‌ها در لایهٔ ارسال با entityهای بومی Telegram (bold و code) قالب‌بندی
می‌شوند؛ متن بیرونی به‌عنوان HTML اجرا نمی‌شود. شمارهٔ صفحه و عددهای نمایشی
فارسی‌اند؛ شناسه، تلفن، ایمیل، رمز، JSON و فرمان قابل کپی دست‌نخورده می‌مانند.
فهرست کاربران به کارت‌های متنیِ فهرست‌وار با وضعیت و نقش تبدیل شده و تاریخ ثبت
و آخرین ورود (اگر API برگرداند) جلالی است. تاریخ «ارسال» از ساعت سرور با منطقهٔ
Asia/Tehran محاسبه می‌شود و به معنی تاریخ ثبت رکورد نیست.
پیام‌های طولانی بدون بریدن محتوا به چند پیام تقسیم می‌شوند؛ offsetهای entity
و زوج‌های UTF-16 ایموجی هنگام تقسیم حفظ می‌شوند.

آزمون قالب‌بندی: `npx tsx scripts/telegram-format-test.ts`.


### مدیریت محاوره‌ای کاربران و حذف پیام رمز

نیازی به فرمان‌های اسلش‌دار نیست: «کاربر دوم را حذف کن»، «کاربران فعال را نشان
بده»، «کاربر با نام … را غیرفعال کن» و «همه کاربران غیرفعال را حذف کن» را بنویس.
مدل فقط درخواست را به یک برنامهٔ ساختاریافته تبدیل می‌کند. سرور شناسه‌ها را با
فهرست همان مالک/نشست یا UUID صریح خود کاربر تطبیق می‌دهد؛ نام‌ها باید به نتیجهٔ
یکتا برسند. نام مبهم نیازمند انتخاب مجدد است و هر تغییر تأیید جداگانه می‌خواهد.
«همه‌شان» پس از فهرست به کاربران همان فهرست محدود می‌شود؛ محدودهٔ سراسری باید
صریح باشد و در پیشنهاد تأیید نمایش داده می‌شود. خطای مدل هرگز باعث اجرای مستقیم
یا معرفی دستور `/userlist help` نمی‌شود.

ساخت عادی در چهار مرحله است: نام، ایمیل، تلفن و رمز؛ نقش پیش‌فرض `customer`
در خلاصهٔ تأیید نشان داده می‌شود و سرویس همچنان مجازبودن این نقش را کنترل می‌کند.
برای نقش متفاوت بعد از ایجاد، درخواست تغییر نقش بده.
پیام ورودیِ مرحلهٔ رمز (حتی رمز نامعتبر) با Telegram `deleteMessage` حذف می‌شود.
اگر حذف مجاز نباشد یا شکست بخورد، ربات از فرستنده می‌خواهد خودش پیام را حذف کند؛
حذف قطعی یا پاک‌شدن نسخه‌های دیگر تلگرام تضمین نمی‌شود. رمز به مدل فرستاده نمی‌شود
و فقط در جریان موقتِ سرور برای ساختِ تأییدشده نگهداری می‌شود، نه حافظهٔ دائمی.
انقضای پنج‌دقیقه‌ای، لغو، تغییر نشست و پایان کار جریان را غیرقابل استفاده می‌کند؛
این حافظه در cold start از بین می‌رود. این بخش هم فقط مخصوص تلگرام است.
