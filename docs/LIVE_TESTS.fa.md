# تست واقعیِ بدون تغییر اطلاعات

Workflow: **Live read-only checks** در `.github/workflows/live-readonly.yml`.

## آماده‌سازی امن

1. این تغییرات باید با PR بررسی شوند. برای ظاهر شدن دکمهٔ اجرای دستی، workflow باید ابتدا روی شاخهٔ پیش‌فرض (`main`) باشد. ادغام خودکار انجام نمی‌شود.
2. در GitHub مخزن، مسیر **Settings → Environments** یک environment با نام `live-readonly` بسازید. در صورت پشتیبانی مخزن، required reviewers و محدودیت شاخهٔ `main` را فعال کنید تا فقط کد بررسی‌شده به secrets دسترسی داشته باشد.
3. در بخش **Environment secrets** همین environment این چهار مقدار را وارد کنید:

| نام Secret | مقدار |
| --- | --- |
| `WEBHOOK_BASE_URL` | مبدأ HTTPS سرویس کلینیک، بدون مسیر؛ مثل `https://nafasbeautyclinic.ir` |
| `WEBHOOK_USERNAME` | نام کاربری سرویس برای Basic Auth |
| `WEBHOOK_PASSWORD` | رمز سرویس |
| `OPENROUTER_API_KEY` | کلید OpenRouter |

از حساب سرویس با کمترین مجوز، ترجیحاً فقط `users.read`، استفاده کنید. هیچ فایل env یا مقداری از secrets را در چت، PR، کد یا لاگ قرار ندهید. برای این workflow به توکن تلگرام یا `BOT_API_KEY` نیازی نیست.

4. پس از ادغام و تنظیم secrets: **Actions → Live read-only checks → Run workflow**، شاخهٔ `main` را انتخاب کنید. در صورت تنظیم بازبین، اجرا نیاز به تأیید دارد.

## چه چیزی اجرا می‌شود؟

- `GET /api/v1/webhooks/users?page=1&perPage=1`: اتصال HTTPS، پذیرش اعتبارنامه و دسترسی خواندن کاربران را با هم بررسی می‌کند. این تست، مجوزهای نوشتن یا همهٔ endpointها را تأیید نمی‌کند.
- همان GET با `search` تصادفی و غیرشخصی: انتظار نتیجهٔ خالی دارد. این فقط بررسی اولیهٔ فیلتر است؛ در صورت خالی بودن کل فهرست، پشتیبانی search ثابت نمی‌شود و تطبیق نام فارسی یا رفع ابهام نام‌های تکراری را هم ثابت نمی‌کند.
- یک POST به endpoint گفت‌وگوی OpenRouter با مدل دقیق `liquid/lfm-3-1.7b:free` و JSON mode، بدون fallback یا retry. پاسخ باید JSON با `ok: true` باشد. هیچ دادهٔ کلینیک به مدل ارسال نمی‌شود. این یک فراخوانی واقعی است و محدودیت نرخ/سهمیهٔ OpenRouter اعمال می‌شود.

هیچ POST/PATCH/DELETE به کلینیک ارسال نمی‌شود. ساخت، ویرایش، حذف و تغییر گروهی کاربران آزمایش نمی‌شوند. این تست end-to-end ربات یا تلگرام نیست.

## لاگ و خطاها

مخزن عمومی است؛ لاگ‌ها را عمومی فرض کنید. اسکریپت فقط نام ثابت تست، PASS/FAIL، وضعیت HTTP و خطای عمومی چاپ می‌کند؛ رکورد کاربران، نام کاربری، URL سرویس، Authorization، متن پاسخ و متن خام خطا چاپ یا به artifact تبدیل نمی‌شوند. اطلاعات پاسخ فقط در حافظهٔ runner بررسی می‌شوند.

- `401`: اعتبارنامه رد شده؛ `403`: دسترسی رد شده. علت دقیق ممکن است وابسته به سرویس یا پراکسی باشد.
- `429`: محدودیت نرخ یا سهمیه؛ `5xx`: مشکل upstream.
- خطای عمومی شبکه: DNS/TLS/timeout/redirect/JSON نامعتبر؛ جزئیات عمداً مخفی‌اند.
- `unexpected response shape/content`: ساختار پاسخ با شکل‌های `[]`، `{items: []}`، `{rows: []}`، `{data: []}` یا پوشش تو‌در‌توی `data` مانند `{ok: true, data: {items: []}}` سازگار نیست، جستجوی تصادفی نتیجه داده، یا مدل JSON مورد انتظار را برنگردانده است. پاسخ خام را منتشر نکنید.

اتصال runner گیت‌هاب به سرویس کلینیک از قبل تضمین نشده است. تست mock فقط ایمنی و منطق اسکریپت را تأیید می‌کند، نه اتصال واقعی را.

## اجرا روی سیستم خودتان (اختیاری، Node 22)

متغیرها را در فایل محلی و gitignored با نام `.env.local` نگه دارید:

```bash
node --env-file=.env.local scripts/live-readonly.mjs
```

برای تست‌های آفلاین بدون secrets و بدون شبکه:

```bash
node --test scripts/live-readonly.test.mjs
```

# تست جستجوی نام و چرخهٔ واقعی کاربر آزمایشی (دارای عملیات نوشتن)

Workflow جدا: **Live test-user lifecycle (writes)** در `.github/workflows/live-users-lifecycle.yml`.
این workflow فقط دستی و روی `main` اجرا می‌شود؛ workflow قبلی همچنان فقط خواندنی است.

## پیش‌نیاز و تأیید

1. محیطی به نام `live-users-test` بسازید. در صورت امکان required reviewers و محدودیت شاخهٔ `main` را برای آن فعال کنید. ابتدا این workflow باید با PR بررسی و وارد `main` شود.
2. secrets زیر را در همین محیط تنظیم کنید؛ مقادیر را در چت نفرستید:
   - `WEBHOOK_BASE_URL`، `WEBHOOK_USERNAME`، `WEBHOOK_PASSWORD`: حساب سرویس باید مجوزهای `users.read`، `users.write` و `users.manage` داشته باشد.
   - `TEST_USER_EMAIL`: ایمیل اختصاصی آزمایش، تحت کنترل شما، که متعلق به هیچ حساب موجودی نیست.
   - `TEST_USER_PHONE`: شمارهٔ آزمایشی معتبرِ تحت کنترل شما، که متعلق به هیچ حساب موجودی نیست. شمارهٔ تصادفی یا متعلق به بیمار/کارمند استفاده نکنید.
   - `TEST_USER_ROLE_KEY`: کلید نقش معتبر و کم‌دسترسی که خودتان تأیید کرده‌اید. نقش مدیریتی ندهید؛ اسکریپت معنای نقش‌های سرویس را نمی‌داند.
3. ابتدا ترجیحاً روی staging اجرا کنید. ایجاد کاربر ممکن است ایمیل، پیامک، audit log یا سایر side effectهای سرویس را فعال کند؛ پاک‌کردن حساب این آثار را برنمی‌گرداند. سیاست‌های upstream باید از قبل بررسی شوند.
4. از Actions این workflow را روی `main` اجرا و در ورودی confirmation دقیقاً `CREATE_UPDATE_DELETE_TEST_USER` وارد کنید. این ورودی تأیید ساخت، ویرایش و حذف همان حساب جدید است؛ ورودی دیگری باعث skip شدن job می‌شود، نه موفقیت تست.

## گام‌های تست

- جستجوی ایمیل و شمارهٔ آزمایشی؛ هرگونه نتیجه یا پاسخ ناشناخته تست را قبل از ساخت متوقف می‌کند. این کنترل جایگزین unique constraint سرویس نیست.
- ساخت یک حساب با نام فارسی شامل شناسهٔ تصادفی، اطلاعات تماس آزمایشی و رمز قوی تصادفی که چاپ و ذخیره نمی‌شود. تنها UUID پاسخ همین POST به‌عنوان هدف ویرایش و حذف مجاز است؛ هیچ شناسه‌ای از نتایج جستجو برای تغییر انتخاب نمی‌شود.
- جستجوی نام کامل فارسی و بررسی UUID، نام، ایمیل و شمارهٔ حساب ایجادشده.
- جستجوی بخشی از نام (شناسهٔ تصادفی)، و عبارت ناموجود.
- تغییر نام و `isActive: false` همان حساب و بررسی هر دو فیلد در پاسخ جستجوی نام جدید.
- تلاش برای حذف همان UUID در `finally`، حتی اگر مرحلهٔ بررسی یا ویرایش شکست بخورد؛ سپس بررسی نبودن UUID در جستجوی ایمیل و شناسهٔ تصادفی. این تست حذف سخت را از soft-delete تشخیص نمی‌دهد، فقط حذف و غیبت در جستجو را بررسی می‌کند.

جستجوی نام‌های تکراری، fuzzy matching، همهٔ حالت‌های حروف فارسی/عربی، تغییر گروهی، همهٔ فیلدها، و مسیر گفت‌وگو/تأیید بات هنوز تست نمی‌شوند. این تستِ مستقیم API است و دادهٔ کلینیک را به مدل ارسال نمی‌کند؛ به کلید OpenRouter نیاز ندارد.

## محدودیت پاک‌سازی

اگر POST در سرور موفق شود اما اتصال قبل از دریافت UUID قطع شود یا ساختار پاسخ ناشناخته باشد، اسکریپت عمداً هیچ حسابی را از روی جستجو حذف نمی‌کند؛ پیام `create outcome uncertain` چاپ می‌شود. اگر DELETE شکست بخورد نیز پیام `FAIL cleanup` می‌آید. در هر دو حالت حساب اختصاصی `TEST_USER_EMAIL` را **در پنل امن سرویس** بررسی و فقط حساب آزمایشی را دستی پاک‌سازی کنید. پاسخ خام یا مشخصات کاربران را منتشر نکنید.

لغو دستی job، قطع runner یا timeout ممکن است مانع اجرای `finally` شود. اجرا را بی‌دلیل لغو نکنید و پس از شکست، قبل از اجرای مجدد حساب آزمایشی را بررسی کنید. اجرای خودکار مجدد یا retry عملیات نوشتن وجود ندارد.

اسکریپت ساختارهای مستندِ `data` و `items/rows` و شناسهٔ `id` را می‌شناسد. اگر سرویس فیلدها را پنهان یا شماره را normalize کند، ممکن است بررسی دقیق شکست بخورد؛ شکست تست به‌تنهایی به معنی خرابی upstream نیست. به‌جای چاپ پاسخ واقعی باید قرارداد پاسخ را امن بررسی کرد.

تست آفلاین بدون secrets و بدون شبکه:

```bash
node --test scripts/live-users-lifecycle.test.mjs scripts/live-readonly.test.mjs
```
