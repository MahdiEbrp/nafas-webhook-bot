# معماری — چطور کار می‌کند

این سند «چرا»‌ها را توضیح می‌دهد؛ `README.md` «چه‌کار-می‌کند» را.

---

## ۰. توپولوژی

```
  nafasbeautyclinic.ir            ← upstream: داده + وب‌هوک + مجوزها
          ▲  Basic Auth (رمز فقط در env این پروژه)
  این پروژه (Vercel)              ← middleware: AI، proxy، rate limit، audit
          ▲  x-bot-key (+CORS)
  پروژهٔ ورسلی شما                ← downstream: اپ/ربات/پنل
```

این پروژه **نه** مالک داده است و **نه** پایگاه داده دارد. هر سه لایه‌اش (منیفست، مجوز، توضیح) فقط
«ترجمه و کنترل» می‌کنند. اگر این واسط را خاموش کنی، سایت دقیقاً مثل قبل کار می‌کند.

دو دهانهٔ ورودی دارد: `/api/chat` (هوشمند) و `/api/proxy` (خام). هر دو به همان کلاینت وب‌هوک
(`lib/webhooks/client.ts`) می‌رسند، پس هر دو یک rate limit، یک لاگ و یک allowlist دارند.

---

## ۱. مسئله، به زبان ساده

سایت یک API خوب دارد: `/api/v1/webhooks/*` با Basic Auth، مجوز، صفحه‌بندی و خطاهای استاندارد.
ولی استفاده از آن سه چیز لازم دارد: انگلیسی، دانش فنی، و دانستن اینکه «کدام آدرس برای کدام کار».
کاربر کلینیک هیچ‌کدام را ندارد.

پس ربات سه کار می‌کند:

1. **ترجمه**: فارسی محاوره‌ای → یکی از ۴۹ اکشن مجاز.
2. **اجرا**: همان درخواست HTTP که یک برنامه‌نویس می‌نوشت.
3. **ترجمهٔ برگشتی**: JSON → فارسیِ ساده، در سطح فهمِ بچهٔ ۱۰ ساله.

نکتهٔ کلیدی: بند ۲ **هرگز** به مدل سپرده نمی‌شود.

## ۳. چهار لایه، و چرا هر لایه لازم است

### لایهٔ ۰ — منیفست (`lib/features/manifest.ts`)

همه‌چیز از اینجا شروع می‌شود. برای هر بخش: نام فارسی، توضیح بچه‌گانه، کلمه‌های کلیدی، و هر اکشن با:

```
{ id, method, path, permission, danger, needsConfirmation, fields[] }
```

سه مصرف‌کننده دارد: پرامپت مدل (نسخهٔ فشرده)، `/api/features` (نسخهٔ کامل)، و `docs/FEATURES.fa.md` (نسخهٔ انسانی).
**منبع واحد حقیقت** است: اضافه‌کردن یک route جدید = یک بلوک در همین فایل، و بس.

### لایهٔ ۱ — برنامه‌ریز (`lib/bot/planner.ts`)

سه چیز را با هم ترکیب می‌کند:

```ts
guess   = routeMessage(message)      // کلمه‌های کلیدی + فعل، آفلاین
slots   = extractSlots(message)      // uuid، تلفن، روز، ساعت، قیمت، ظرفیت، نام
modelPlan = complete(json:true)      // مدل مجانی، با guess و slots به‌عنوان راهنما
```

- `guess` و `slots` به مدل **به‌عنوان راهنما** داده می‌شوند (نه به‌عنوان دستور) → مدل روی مسیر درست می‌ماند.
- خروجی مدل با Zod پارس می‌شود؛ اگر شکل نداشت، **یک** درخواست ترمیم می‌رود.
- `validatePlan` بررسی می‌کند که `actionId` در منیفست هست و نوعش با intent می‌خواند
  (مثلاً `delete` با `intent:"read"` → رد می‌شود).
- اگر مدل کلاً بمیرد: `routerOnlyPlan` با `guess` + `slots` پلن می‌سازد و `trace.notice` توضیح می‌دهد چرا.

چرا دو مرحله؟ چون وقتی یک مدل کوچک هم‌زمان باید «بفهمد» و هم «قشنگ حرف بزند»، هر دو را نصفه انجام می‌دهد.

### لایهٔ ۲ — دروازهٔ ایمنی (`lib/bot/index.ts` + `session.ts`)

| danger | رفتار |
| --- | --- |
| `read` | فوراً اجرا |
| `write` | کارت تأیید (مگر `ALLOW_AUTO_WRITE=true`) |
| `destructive` | همیشه کارت تأیید، حتی با `ALLOW_AUTO_WRITE` |

کارت تأیید =
`{ token (uuid v4, یک‌بارمصرف, ۱۰ دقیقه), sessionId, plan, summaryFa }`

قفل‌ها:

- `takePending` توکن را **حذف** می‌کند → تک‌بارمصرف.
- `record.sessionId !== sessionId` → رد. پس کسی نمی‌تواند تأییدیهٔ دیگری را بدزدد.
- `approve:false` → هیچ درخواستی نمی‌رود و در حافظه ثبت می‌شود.

### لایهٔ ۳ — مجری (`lib/bot/executor.ts`)


سه سؤال را جواب می‌دهد: **آیا کامل است؟**، **چه چیزی می‌فرستیم؟**، **چه چیزی نمی‌فرستیم؟**

```
REQUIREMENTS[actionId] = { path:[], body:[], anyOf:[] }
```

- کمبود → `needs_info` با `FIELD_QUESTIONS_FA` (سؤال فارسی، نه اسم فیلد).
- `id` باید uuid باشد؛ «علی» uuid نیست → سؤال، نه فراخوانی.
- `pickAllowed` فقط `action.fields` را رد می‌کند → `isAdmin`, `role`, `__proto__` حذف می‌شوند.
- `sanitizeNode` بازگشتی: ارقام فارسی → لاتین، `"1"` → `1` برای فیلدهای عددی، رشته‌های خالی حذف.
- `GET` → query string؛ `POST/PATCH` → JSON body؛ `DELETE` → بدون body.
- برای `bookings.create` پیش‌فرض‌های پروژهٔ مقصد (`termsAccepted:true`, `locale:"fa"`) پر می‌شود.

### لایهٔ ۴ — توضیح‌دهنده (`lib/bot/explainer.ts`)

- `fallbackAnswer` همیشه ساخته می‌شود: جمع‌بندی لیست (تا ۵ مورد)، ترجمهٔ وضعیت‌ها، پیام خطای مهربان.
- مدل مجانی هم صدا زده می‌شود؛ اگر جوابش **کوتاه‌تر از ۸ کاراکتر** بود یا **انگلیسی/پر از ژارگون** بود، نسخهٔ fallback جایگزین می‌شود.
- ترجمهٔ خطاها در یک جدول است: `WEBHOOK_FORBIDDEN` → «این کار را برای ربات باز نکرده‌اند…». هیچ‌وقت `403` خام به کاربر نشان داده نمی‌شود.

## ۴. استراتژی مدل مجانی (`lib/openrouter/client.ts`)

```ts
for (model of chain)            // ۵ مدل مجانی
  for (attempt of 0..retries)   // ۲ تلاش
    try  → برگرد
    catch:
      401/402/408/429/5xx → backoff کوچک، تلاش بعدی
      بقیه (400، مدل وجود ندارد) → مستقیم مدل بعدی
همه شکست خوردند → throw { code:"ALL_MODELS_FAILED", attempts:[...] }
```

- `attempts` در پاسخ `trace` و لاگ‌ها می‌آید → می‌توانی ببینی کدام مدل چرا رد شد.
- `parseJsonLoose`: پارس مستقیم → بلوک ```` ```json ```` → اولین `{…}` → حذف کامای انتهایی.
- `maxDuration: 60` در Vercel برای همین زنجیره است. اگر خیلی کند بود: مدل‌ها را کم کن یا `MODEL_TIMEOUT_MS` را پایین بیاور.

## ۴.۵. حالت واسط خام (`/api/proxy`)

برای وقتی که برنامهٔ ورسلی از قبل می‌داند چه درخواستی می‌خواهد. چرا مسیر سایت را مستقیم صدا نزند؟

| دلیل | جزئیات |
| --- | --- |
| رمز | `WEBHOOK_PASSWORD` فقط در env این پروژه است؛ مرورگر و پروژهٔ ورسلی آن را ندارند |
| سطح حمله | `lib/proxy/allowlist.ts` مسیر+متد را با منیفست تطبیق می‌دهد؛ `PUT`، `/api/v1/users`، `{resource}` ناشناس → `404 NOT_ALLOWED` |
| یکپارچگی لاگ | همهٔ درخواست‌ها یک `x-request-id` و یک خط لاگ دارند |
| CORS | سایت لازم نیست به مرورگر CORS بدهد؛ فقط `ALLOWED_ORIGINS` این واسط |

مسیر رسیدن به مجری:

```
/api/proxy/[...path]  →  cors + bot key + rate limit
                      →  matchAllowedCall(method, pathname)   // منیفست
                      →  extractPathParams()                   // :id
                      →  callWebhook()  →  upstream
                      →  همان پوشش { ok, data } / { ok:false, error }
```

یعنی **هیچ منطق تازه‌ای** لازم نبود: allowlist از همان منیفستی ساخته می‌شود که AI هم از آن می‌خواند.
اضافه‌کردن اکشن جدید، خودکار مسیر پروکسی را هم باز می‌کند (و بستنش هم خودکار است).

## ۴.۶. لایهٔ تلگرام (`/api/telegram/*`)

```
تلگرام ──POST /api/telegram/webhook (secret) ──► handler
                                                    │
      ┌─────────────────────────────────────────────┼──────────────┐
      ▼                                             ▼              ▼
  /start, /menu, f:…                     متن آزاد فارسی        دکمهٔ c:/x:
  (بدون AI، بدون HTTP)                        │              (تأیید نوشتن)
                                              ▼                     │
                                        handleChat ◄───────────────┘
                                              │
                                    ┌─────────┴─────────┐
                                    ▼                   ▼
                             پاسخ فارسی + دکمه‌ها    suggestNext() → AI
```

سه نکتهٔ طراحی:

1. **هیچ منطق تجاریِ تازه‌ای اضافه نشد.** تلگرام فقط یک «پوست» روی `handleChat` است؛
   بنابراین مجوزها، کارت تأیید و منیفست عیناً همان‌اند. دکمهٔ `a:<actionId>` هم از مسیر
   `direct` همان `handleChat` رد می‌شود، نه از یک مسیر موازی.
2. **پیمایش، هوش مصنوعی نمی‌خواهد.** `m`/`h`/`f:` فقط متن و دکمه برمی‌گردانند: صفر هزینه، صفر تأخیر.
   تنها جایی که مدل صدا زده می‌شود `a:`, متن آزاد و «پیشنهاد قدم بعدی» است.
3. **کیبورد = دادهٔ اعتبارسنجی‌شده.** `suggest.ts` هر پیشنهاد مدل را با منیفست چک می‌کند
   (`read` + بدون `:id` + موجود بودن)، و `keyboard.ts` سقف ۶۴ بایتی `callback_data` را
   قبل از ساختن دکمه اعمال می‌کند. یعنی یک مدل مجانیِ هذیانی نمی‌تواند دکمهٔ «حذف همه» بسازد.

### لاگین خودکار

`instrumentation.ts` → `register()` → `setup.ts::autoSetupOnBoot()`:

```
getMe()           → توکن واقعی است؟ (نام و آیدی ربات لاگ می‌شود)
getWebhookInfo()  → آدرس فعلی همان است؟
setWebhook()      → اگر نه: ثبت (با secret_token)
```

`ensureWebhook()` ایدمپوتنت است: ری‌استارت‌ها ثبت را تکرار نمی‌کنند. روی Vercel این تابع در
اولین کولد-استارت هر instance اجرا می‌شود؛ همین «بعد از استارت» است که خواسته شده بود.

### هویت: چرا OTP نداریم و چه داریم

`lib/telegram/identity.ts`. سه لایه:

1. **چیزی که سایت می‌دهد:** فقط Basic auth. بخش SMS در `schema.ts` هست ولی route ندارد →
   پس نه ارسال کد ممکن است، نه تأیید کد.
2. **جایگزین درست:** شماره‌ای که تلگرام خودش با پیامک تأیید کرده. دکمهٔ `request_contact`
   شمارهٔ *خودِ کاربر* را می‌فرستد (`contact.user_id === from.id` اجباری است، وگرنه کارت
   فوروارد‌شده می‌تواند جعل هویت باشد).
3. **تصمیم مجوز با دادهٔ سایت:** `GET /api/v1/webhooks/users?search=<phone>` و تطبیق دقیق
   شماره، بعد بررسی `isActive` / `isBanned`. نتیجه: `{ clinicUserId, fullName, roleKey }`.

**کد کشور و فرمت ذخیره‌سازی.** تلگرام شماره را بین‌المللی می‌فرستد (`+98912…`)، ولی دیتابیس
سایت ممکن است هر شکلی ذخیره کرده باشد. `normalisePhone` همه را به `09xxxxxxxxx` می‌برد، و
`searchVariants` چند املا می‌سازد چون `search` در سایت «شامل بودن رشتهٔ خام» است. اگر هیچ‌کدام
نزد، `findUserByPhone` حداکثر ۳ صفحهٔ ۵۰تایی را اسکن و **مقایسهٔ نرمال‌شده** می‌کند؛ تصمیم
همیشه با تساوی دقیق است، نه پیشوند. اعداد غیرایرانی (`+1…`, `+44…`) صریحاً رد می‌شوند.

قفل اصلی: `identityGate` **قبل از** `handleChat` اجرا می‌شود، پس چتِ تأییدنشده حتی یک
درخواست هم به دادهٔ کلینیک نمی‌زند (تست `چتِ ناشناس اول شماره می‌خواهد` همین را بررسی می‌کند).

### تلگرام و idempotency

تلگرام اگر `200` نگیرد همان آپدیت را دوباره می‌فرستد. برای یک ربات اداری این یعنی
«دو نوبت ساخته شد». پس: همیشه `200` + `update_id` در حافظهٔ کوتاه‌مدت.
خطای داخلی هم `200` برمی‌گرداند (و در لاگ ثبت می‌شود) تا storm نشود.

## ۵. چه چیزی عمداً ساخته نشد

| تصمیم | چرا |
| --- | --- |
| بدون دیتابیس | صفر-پیکربندی؛ حافظه فقط برای تأییدیه/آخرین نوبتِ گفت‌وگو. مسیر ارتقا در `session.ts` مستند شده. |
| بدون صفحات React | درخواست «فقط بک‌اند»؛ تنها یک HTML خالص برای مستندات/تست. |
| بدون کش پاسخ‌های upstream | در کلینیک، «نوبت‌های امروز» باید تازه باشد؛ کش می‌تواند خطرناک باشد (`Cache-Control: no-store`). |
| بدون tool-calling به‌عنوان مسیر اصلی | مدل‌های کوچک مجانی در `tools` پرسه می‌زنند؛ JSON + اعتبارسنجی پایدارتر است. تعریف tool برای آینده در `/api/features?shape=tools`. |
| تأیید انسانی برای هر نوشتن | یک ربات اداری که خودسرانه حذف کند، حتی اگر ۹۹٪ درست باشد، قابل اعتماد نیست. |

## ۶. مسیر اضافه‌کردن یک قابلیت جدید

مثال: پروژه route پیامک را اضافه کرد.

1. در `lib/features/manifest.ts` بخش `sms` را `available: true` کن و اکشن‌ها را با `path/permission/fields` بنویس.
2. در `lib/features/requirements.ts` فیلدهای لازم را اضافه کن.
3. اگر فیلد فارسی‌اش سؤال لازم دارد، به `FIELD_QUESTIONS_FA` اضافه کن.
4. `npm run build:catalog && npm run selftest` — تمام. پرامپت مدل هم خودکار به‌روز می‌شود، چون از منیفست ساخته می‌شود.

هیچ‌جای دیگر لازم نیست تغییر کند؛ نه router، نه executor، نه API.
