# مدیریت ایمیل از تلگرام

این راهنما پیاده‌سازی محاوره‌ایِ تمام مسیرهای موجود در
`beauty-clinic/app/api/v1/admin/email` را پوشش می‌دهد؛ مرجع با commit
`af5d4f872a7ac8f75fa1e6780e788e83557c5100` بررسی شده است.

## عملیات و دسترسی

همهٔ مسیرها به نشست مجاز نیاز دارند؛ مجوزهای دقیق را API اصلی اعمال می‌کند.
مدیریت فقط در گفت‌وگوی خصوصی تلگرام انجام می‌شود و فرمان اسلش لازم نیست.

| مسیر زیر `/api/v1/admin/email` | روش‌ها و کارکرد |
| --- | --- |
| `/overview` | GET — آمار ارسال، وضعیت سرویس‌ها و تازه‌ترین گزارش‌ها |
| `/providers` | GET — جست‌وجو/فیلتر/صفحه‌بندی؛ POST — ساخت سرویس ایمیل |
| `/providers/:id` | GET — مشاهده؛ PATCH — ویرایش؛ DELETE — حذف نرم/غیرفعال‌سازی |
| `/providers/:id/test` | POST — ارسال ایمیل آزمایشی و ثبت سلامت سرویس |
| `/messages` | GET — گزارش‌ها؛ POST — ارسال به یک یا چند گیرنده |
| `/messages/:id` | DELETE — حذف رکورد گزارش داخلی |
| `/recipients` | GET — کاربران فعال و بدون مسدودی که نشانی ایمیل دارند |
| `/templates` | GET — جست‌وجو/فیلتر/صفحه‌بندی؛ POST — ساخت قالب دو‌زبانه |
| `/templates/:id` | GET — مشاهده؛ PATCH — ویرایش؛ DELETE — حذف نرم/غیرفعال‌سازی |

هیچ endpoint گروهی برای سرویس‌ها/قالب‌ها، مشاهدهٔ تکی گزارش ارسال، ویرایش یا لغو
ایمیل ارسال‌شده در این زیرشاخه وجود ندارد؛ ربات آن‌ها را جعل نمی‌کند. گزارش ارسال
را ابتدا فهرست کن و سپس ردیف دیده‌شده را انتخاب کن. جست‌وجوی گزارش در API اصلی با
نشانی گیرنده (به‌صورت هش) یا شناسهٔ سرویس‌دهنده انجام می‌شود، نه هر شناسهٔ دلخواه.

## ارسال و تست: ایمیل واقعی

- «ایمیل بفرست» یک فرم محلی باز می‌کند: گیرنده‌ها، متن دلخواه یا قالب، موضوع، زبان،
  نوع ارسال، سرویس (یا انتخاب پیش‌فرض سرور)، فرستندهٔ جایگزین و نام کمپین. برای قالب،
  زبان و متغیرها هم پرسیده می‌شود. قالب سفارشی و حداکثر ۱۰۰۰ گیرنده مطابق محدودیت API است.
- قبل از تأیید، پیش‌نمایش گیرنده‌ها، موضوع و متن نهایی نمایش داده می‌شود. ارسال تنها
  پس از «تأیید» انجام می‌شود؛ تأیید یک‌بارمصرف است.
- ارسال نوع `marketing` می‌تواند به گیرندگان واقعی پیام تبلیغاتی بفرستد؛ پیش از تأیید
  رضایت گیرندگان و فهرست را بررسی کن. پذیرش سرویس‌دهنده به معنی تحویل قطعی یا قرارگرفتن
  در صندوق ورودی نیست؛ وضعیت `delivered` را در گزارش‌ها بررسی کن.
- برای هر پیشنهاد ارسال، ربات یک کلید idempotency می‌سازد و درخواست HTTP را خودکار
  تکرار نمی‌کند. این تضمین exactly-once نیست؛ در قطع ارتباط، سرویس ممکن است ایمیل را
  پذیرفته باشد. ابتدا گزارش را بررسی کن و از ارسال مجدد عجولانه بپرهیز.
- تست سرویس، مگر برای نوع `fake`، یک ایمیل واقعی به گیرندهٔ انتخابی می‌فرستد و نتیجهٔ
  سلامت را ثبت می‌کند. تست هم پیش‌نمایش و تأیید جداگانه دارد. پاسخ موفق فقط پذیرش تست
  توسط سرویس است، نه تضمین تحویل.
- قالب‌های ایمیل دو ترجمهٔ فارسی و انگلیسی دارند. در ویرایش، اگر `translations` ارسال
  شود، هر دو زبان جایگزین می‌شوند. کلید قالب قابل ویرایش نیست.

## حریم خصوصی و امنیت

- آدرس گیرنده، متن ایمیل، متغیرها و رمز/توکن سرویس در فرم‌های محلی وارد می‌شوند؛ به
  planner/model یا تاریخچهٔ چت فرستاده نمی‌شوند. پیام هر مرحله پس از دریافت حذف می‌شود؛
  اگر Telegram اجازهٔ حذف ندهد، ربات هشدار می‌دهد تا کاربر خودش آن را پاک کند.
- پیش‌نویس‌ها در حافظهٔ همان process، وابسته به نشست و حداکثر پنج دقیقه نگهداری می‌شوند؛
  بین restart یا instanceها پایدار نیستند. تغییر نشست، انصراف، تغییر دامنهٔ کاری و انقضا
  پیش‌نویس را لغو می‌کنند.
- نمایش سرویس، نام‌کاربری، رمز، چهار رقم آخر رمز و خطای خام سرویس‌دهنده را افشا نمی‌کند.
  نشانی‌های گیرنده فقط در خصوصی و برای نشست مجاز نمایش داده می‌شوند. جزئیات گزارش نیز
  به فیلدهای امن محدود شده است.
- نوع‌های سرویس `gmail`, `outlook`, `yahoo`, `custom`, `liara`, `fake` هستند. برای
  SMTP، میزبان‌های localhost، دامنهٔ محلی و IP literal پذیرفته نمی‌شوند؛ Liara باید
  HTTPS باشد. این محدودیت جلوی DNS rebinding یا resolve شدن یک دامنهٔ عمومی به شبکهٔ
  خصوصی را به‌تنهایی نمی‌گیرد؛ سیاست شبکهٔ سرور/adapter همچنان لازم است. ربات هیچ اتصال
  مستقیمی به میزبان ایمیل برقرار نمی‌کند.
- حذف سرویس یا قالب نرم است و آن را غیرفعال می‌کند؛ انتخاب سرویس پیش‌فرض جدید، قبلی را
  کنار می‌زند. حذف گزارش، رکورد پایگاه‌داده را پاک می‌کند، **نه ایمیل را از صندوق گیرنده**.

## آزمون

`npm run email:test` از HTTP mock استفاده می‌کند و هر ۱۶ عملیات، تأییدهای محلی،
پنهان‌سازی، نشست/خصوصی‌بودن، تداخل snapshot و نبود retry را بررسی می‌کند. `npm run check`
هم تست را در خودآزمایی پروژه اجرا می‌کند. در توسعه یا تست هیچ SMTP/ارسال واقعی انجام
نمی‌شود.
